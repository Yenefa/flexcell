# 端到端验证：无意义重试消失，且**真实增益一个没丢**

## 设计：同 16 实例，修复前 vs 修复后

两批都用 seeds 8100/8200 的同一组 16 个实例。
**这专门用来测修复本身**，而不是测泛化。

| 指标 | 修复前 | 修复后 |

| **重试后仍通过（无意义重试）** | **2** | **0** |
| 配对增益 | 0 | **2** |
| 配对损失 | 0 | **0** |
| goal_check 跳过 | 0 | 3 |
| goal_check 拒绝（多段任务） | 0 | 2 |

## 关键安全性质被证明

那 **2 例增益**（`HO-274c7aaa6485`、`HO-e2d3ed8c2437`）
**正是 goal_check 拒绝跳过的**。

如果它按第一版的逻辑（比对每一段目标）判断，这两例会停在第一段目标附近、
被误判为「已达成」——**2 个增益会直接消失**。

**安全方向不是靠推理保证的，是靠这两例真实数据证明的。**

## 我又抓到自己一个标注错误

第一版归档表把 `HO-2f52569ef5ca` 标成 `SATISFIED(stages=2)`，
只因为 `goal_check.json` 里有 `stages` 字段。

**它的决策是 `resume`，意思是检查比对后判定「未达成」——正好相反。**

已改为由**决策理由**判定，不由文件是否存在判定：

| 判据 | 结论 |
| --- | --- |
| 决策理由含 `goal already satisfied` | 跳过 |
| `goal_check.decision` 含 `REFUSED` | 拒绝 |
| 有 stages 但走了恢复 | **检查后未达成** |

## 不能归因于修复的数字

B 通过从 16/16 降到 13/16 **与修复无关**——
修复只在恢复阶段运行，**attempt 1 完全不受影响**。
差异来自两批世界的随机性（每例重新开世界）。

所以正确的读法是：**同一批实例上，修复前有 2 次无意义重试，修复后为 0**，
而不是「修复让 B 变差」。
