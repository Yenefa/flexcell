# 跨类型泛化：约束「什么时候」而不是「放哪里」

## 为什么之前的泛化不够

T12 要求重复路线，T13 要求几何条件判断。
**两者都只变世界、不变要求的结构**——规划器可以从不思考「先做哪个」
而照样通过。

新模板 **T14_ordered_pair**：

```
Put both blocks in the red bin. The blue block must be put there FIRST,
then the red block. Doing it in the other order is not acceptable even
if both end up in the right bin.
```

顺序成为目标的一部分。**验收器已支持 `order` 子句（从 `move_sequence` 判分），未改一行。**

## 结果（16 例，全新种子 9300/9400，零重叠）

| 指标 | 值 |
| --- | --- |
| **规划层顺序合规** | **16/16 = 100%（80.6–100%）** |
| 执行层顺序合规 | 14/16 = 87.5%（64.0–96.5%） |
| arm B 通过 | 14/16 = 87.5% |
| **arm R 通过** | **16/16 = 100%** |
| **真正颠倒顺序** | **0** |

## 关键：**从未颠倒顺序**

| 类别 | 数量 | 含义 |
| --- | --- | --- |
| in-order | 14 | 序列完整且顺序正确 |
| **INCOMPLETE** | 2 | 只观察到第一个移动——运行在半途停下 |
| **WRONG-ORDER** | **0** | **没有一次把工作做反** |

2 例 INCOMPLETE 的实测证据：

```
HO-2efba46248da: planned ['target_box_a','target_box_b']
                observed ['target_box_a']   matched=1 out_of_order=[]
HO-d3ab212142de: planned ['target_box_b','target_box_a']
                observed ['target_box_b']   matched=1 out_of_order=[]
```

`out_of_order=[]` 说明**没有一个移动是错的**，只是第二个从未发生。
两例都经恢复后通过。

## 我又一次把自己的工具标错了

第一版分析器用一个布尔值判断「是否合规」，我把 `False` 读成
**「规划对了但执行丢了顺序」**。

**这是错的。** 证据是 `observed` 只有一个物体、`matched=1`、`out_of_order=[]`，
含义是**第二个移动根本没被记录**，不是顺序错了。

如果那样报出去，我会凭空造出一个从未发生的失效模式。

已改为三态：

| 状态 | 判据 |
| --- | --- |
| `in-order` | 完整且顺序正确 |
| `INCOMPLETE` | 观察序列是要求的**正确前缀** |
| `WRONG-ORDER` | 有移动但不在要求的序列上 |

**这与前几轮同一类错误**：把「没做到」和「做错了」混为一谈。
两者对 agent 含义完全不同——前者是执行没走完，后者是理解错了。

## 这说明什么

**共识别的时序约束被正确理解并执行**：
规划 16/16、执行 14/16、颠倒 0/16。
剩余 2 例是执行未完成（与前几轮定位的释放 stall 同源），
而 `goal_check` + 恢复把它们都救了回来。

这是 Level 8 的实质性加强：**不只是换种子，而是换要求的结构**。
