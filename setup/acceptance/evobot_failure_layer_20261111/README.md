# 失败归因：64 例中 **0 例**归因于规划

## 我想纠正自己的一个说法

我此前多次说：「经验不改计划，所以 Level 7 Transfer 未观察到」。
这句话把原因指向**投递机制**。

**本轮测量表明那个解释是错的。**

## 测量

对四个已校验批次的**每一次首试失败**做层级归因：

| 项 | 数量 |
| --- | --- |
| 参与统计的运行 | **64** |
| 干净通过 | 49 |
| **可归因于规划** | **0** |
| 可归因于执行 | **15** |
| 无法归因 | 0 |

逐批：

| 批次 | 通过 | 规划 | 执行 |
| --- | --- | --- | --- |
| batch1 | 14 | **0** | 2 |
| batch2 | 14 | **0** | 2 |
| batch3 | 10 | **0** | 6 |
| batch4 | 11 | **0** | 5 |

## 15 例执行失败里是什么

| 类别 | 数量 | 说明 |
| --- | --- | --- |
| 技能层误报（false failure） | 8 | 世界已满足目标，任务却报失败 |
| 真实 grasp/stall | 7 | 释放确认失败或运行未走完 |

**没有一例是「计划写错了」。**

## 所以 Level 7 的结论要改

| 旧说法 | 新结论 |
| --- | --- |
| 经验不改计划 → **投递机制有问题** | 经验不改计划 → **规划层没有可修的错** |

这两种解释对「接下来该做什么」含义相反：

- 若是投递坏了：应该改进经验路由、改 prompt；
- 若是没有可修的错：**再怎么改投递都不会有效**，能力缺口在执行层。

**我此前一直在按第一种解释行动**（路由审计、可执行性审计、B/C 对照），
而证据支持第二种。

## 为什么必须先证明分类器能识别规划失败

「0 例规划失败」这句话，如果分类器**只会输出 EXECUTION**，就毫无意义。

所以测试里**大部分是反向用例**——必须判为 PLANNER 的情形：

| 测试 | 期望 |
| --- | --- |
| 没有产出计划 | PLANNER |
| `plan must declare every observed object` | PLANNER |
| `no JSON in reply` | PLANNER |
| 技能 stall | EXECUTION |
| **无任何证据** | **UNKNOWN（不得洗成 EXECUTION）** |
| 分类器能输出全部三类 | 断言集合相等 |

## 测试抓到我一个真 bug

`native_fsm_trace` 是**列表**，`str(list)` 得到 `"['']"`，**永不为空**。
于是「无证据」判断失效，**所有无证据的运行都被判成 EXECUTION**。

**这正是「不可测量的零不是零」的同一形状**——一个永远不会失败的检查。已修。

- 不宣称规划层永远不会有错（只在这 64 例与这 3 个模板上）；
- 不宣称执行层是**唯一**缺口（Level 4 Develop 仍未达成）；
- 归因依据 `failure_evidence.json` 与恢复决策的文本，非独立验证；
- **未上真机，M0**。

## 这条结论的价值

它把「经验为什么不生效」从一个**待修机制**变成一个**已解释的边界条件**：
在规划已经 0 错的情况下，任何规划级经验注入都只能增加开销。

这也解释了此前测到的 **+3% token 纯开销**——不是路由错了，是**没有东西可送**。
