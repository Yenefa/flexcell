## 假设判定

### H1「方差由墙钟调度造成」—— **作为唯一解释被推翻**

去掉墙钟限速后**方差没有消失，反而更大**（154.9 vs 135.2 mm）。
所以「实时调度」不是方差的唯一来源。

### 但 H1 也**不是全错**——失效模式变了

| | RTF=1 | RTF=0 |
| --- | --- | --- |
| 接触丢失提前终止 | 4/5（lost_at 3,4,3,0,0 中的多数） | **1/5** |
| 跑满 5 增量 | 2/5 | **4/5** |

去掉墙钟限速后，**「接触丢失 → break」几乎不再触发**。
这说明之前看到的「接触丢失」有一部分是墙钟调度造成的**测量伪影**，不全是物理滑脱。

### 剩下真正分叉的是「接触是否建立」

试次 1：`contact_made=False`，末端走完 160mm，方块只动 1.83mm。
试次 2–5：`contact_made=True`，方块动 61–157mm。

**同样的世界、同样的目标、同样的高度，末端有时碰到方块，有时完全没碰到。**

---

## 一个重要警告：RTF=0 不是真正 lockstep

Gazebo 的 `real_time_factor=0` 是「不限速、尽快跑」，**不是确定性步进**。
仿真时间仍可能快于 ROS 指令到达，物理步进与指令的对齐关系依然不保证可重复。

**因此本对照只能否定「墙钟限速是唯一原因」，不能证明剩下的方差来自几何。**

另外，RTF=0 下仿真快于墙钟，**每个增量末尾的物体位姿采样可能读到过期状态**。
所以 `lost_at` 的改善有可能是测量时序变化，而不是物理改善——这一条**未验证**。

---

## 通过率不能宣称提升

2/5 → 3/5 看起来是进步，但 **n=5 对 n=5**，这个差异完全在噪声内。
且对照里出现了新的失败模式（156.77mm 超过 150mm 上限）。

**不得写成「固定步进提高成功率」。**

## 十类归因更新

| 类别 | 状态 |
| --- | --- |
| Control（接触高度） | ✅ 实测效应，解释均值 |
| Control（丢失后 break） | ✅ 代码事实，但其触发频率受调度影响 |
| Tooling（虚拟 link 无碰撞几何） | ✅ 实测到，**仍未证实为方差主因** |
| **Runtime（仿真确定性）** | ✅ **实测：相同输入产生 135–155mm 方差，机制 UNKNOWN** |
| **Grasp / 接触建立** | ⚠️ **新的分叉点：contact_made 有时 False，原因 UNKNOWN** |
| Environment / Perception / Planning / Kinematics / State Management / Model Reasoning | ❌ 排除或无证据 |

**根因状态仍然是 UNKNOWN。** 这轮实验的价值是把问题从
「为什么推不远」缩小到「为什么末端有时根本没碰到方块」，
并排除了一个我此前倾向的解释。

## 下一步该做什么（本轮不做）

要真正判定，需要**接触首帧的两根手指位姿**：
在 `ContactTrace` 日志里定位 `gripper_*_link` 与方块第一次接触的仿真时刻，
比较 `contact_made=True` 与 `False` 两次运行在该时刻的手指相对位置。

若位姿不同 → 归因于运动/时序；若位姿相同而结果不同 → 归因于物理引擎非确定性。

**这需要在证据流水线里记录逐帧手指位姿，是新的实验，不是再调一次参数。**
