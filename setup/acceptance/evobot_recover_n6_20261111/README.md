# Level 3 Recover — 首次在机器人上运行（恢复率 1/2）

## 为什么测这个

连续两轮证明：C 的经验通道（改 prompt）**没有效果**。上轮已诊断出真正瓶颈在
**执行层**——Agent 规划 6/6 正确，失败都是 `err 61/62`。所以本轮把恢复接进运行器，
测「能不能从失败中恢复」，而不是再测 prompt。

## 结果（6 个封存未见实例）

| 指标 | 值 |
| --- | --- |
| 首次即成功 (FIRST_TRY) | 4 |
| **恢复成功 (RECOVERED)** | **1** |
| 仍失败 (STILL_FAIL) | 1 |
| **恢复率** | **1/2 = 50%** |
| 最终通过率 | 5/6 = 83% |
| **False Success Rate** | **0/6 = 0.0%** |

### 成功的那一例（真实恢复的证据）

`HO-b81a5ae02d6d`：
```
attempt 1: outcome=1 err=62  committed=[target_box_a-0]
  -> 剔除已提交阶段，用实测位置重建剩余阶段
     initial_objects 从声明值 (0.22,0) 改为实测 (0.093,-0.157)
     stages 从 2 段减少到 1 段 (target_box_b-1)
attempt 2: outcome=0 err=0
独立验收: passed=True, false_success=False
```
**grading keys 全程未变**（`clearance_m`、`position_tolerance_m` 与首次计划完全相同）。

### 失败的那一例是真实几何冲突

`HO-90899d657e68`：恢复后 `err 60 declared destination occupied`。
`box_a` 已落在 `zone_1` 偏移位，`box_b` 的目标点被它占用。
**这是真实物理约束，不是恢复逻辑错误。** 正确做法需要动态选点，本轮未实现。

## 触发规则（关键设计）

**恢复由「执行结果」触发，绝不由验收结果触发。**
若因验收器判 FAIL 才重试，那是在制造成功。验收器只在**所有尝试结束后**
对最终世界状态判一次分。

## 运行中发现并修掉的三个真实缺陷

### 1. respread 什么都没改（第一次跑，恢复率 0/2）
原实现按「落点完全相等」分组，但计划构建器已把同箱阶段偏移 56mm，
因此**分组永远为空**，`plan_retry.json` 与 `plan.json` 字节相同，重试必然同样失败。
已改为按**距离聚类**。

### 2. 56mm 间距本身就不够
clearance 是 50mm，实测漂移约 10mm → 有效间距掉到 48mm，必然冲突。
改为 90mm 间距（更保守，不是放宽阈值），并在越出箱半径时 `ValueError` 拒绝。

### 3. 部分提交后重放整个计划是错的
若第一次已提交某些阶段，世界已改变，计划声明的 `initial_objects` 不再成立，
必然 `state drift`。新增 `resume` 路径：**从实测位置重建剩余阶段**。

这正是「恢复」与「重试」的区别——第 2 项修复让恢复从 0/2 变成 1/2。
