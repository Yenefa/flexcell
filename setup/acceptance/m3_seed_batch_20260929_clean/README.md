# E-009 — first official M3-seed benchmark batch (authoritative)

**These are the numbers to quote.** 70 episodes: S1×20, S2×20, S5×20, S7×10,
policy = `FSMPolicy` (`decision_policy=fsm`, verified from the live startup
banner `policy=fsm v1.0`), headless, on the RTX 4060 laptop (WSL2 Ubuntu-24.04,
no hardware GL → llvmpipe; see `docs/EXPERIMENTS.md` E-009 for the full
environment caveats).

Every number is regenerated by `setup/95_metrics_report.py` from the replay
store over `batch_merged.jsonl` — no hand-written PASS lines. The report is
committed verbatim as `95_metrics_report.md`.

`REPORT: PASS (70 episodes, 0 replay-dirty)`, 0 `dev/*` buckets. Row level: 70
rows, 19 outcome mismatches, **0 replay-dirty**.

Read the two failure columns correctly:

- the reporter's `REPORT: PASS` is a **replay-integrity** verdict (the store
  reproduces every decision), not "all scenarios succeeded";
- the scenario runner's own verdict is non-zero for S1/S2/S5/S7 because the
  deterministic baseline missed the expected outcome — that is the measurement.

## Caveats that must travel with these numbers

1. **Not comparable to the delivery host's frozen Week-1.5 baseline** — different
   machine, no GPU (headless/llvmpipe), load ~10-12 on 16 threads. At n=20 the
   Wilson CI is ±~19 pp, which dominates run-to-run variance (the same S1 cell
   measured 16/20 in the superseded run and 18/20 here).
2. **The dominant failure mode is physical, not a code defect**: the carry servo
   intermittently fails to lift the box (`box_rise_m ≈ -0.001..-0.004`,
   `inj=None` in `pick.jsonl`) → `ERR_GRASP_FAILED` → with recovery budget 1,
   `ERR_RECOVERY_EXHAUSTED`. This is the declared teleport-servo compromise
   ("magnetic ≠ contact grasping"), and it is what caps S2 at 0.40 (S2 needs two
   successful picks _plus_ a recovery leg).
3. **1 S5 episode succeeded when it should have exhausted** (run 20,
   `dabdd93d`): its `fsm_trace` is all-OK with `error_code 0`, i.e. the `always`
   injection was never armed for that episode. Arming rides a transient topic
   publisher and the client's `INJECT WARNING: no subscriber matched` is
   swallowed by the runner (`capture_output=True`), so a lost arm is silent.
   S5's failure path is therefore n=19 and injection arming is **unverified by
   construction**.
4. **S7 n=10**, below the design's preferred n≥20; the CI is correspondingly wide.

## What is here

| file                                      | what it is                                                                                                              |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `95_metrics_report.md`                    | the metrics report, verbatim (per-cell tables + per-episode rows)                                                       |
| `batch_merged.jsonl`                      | the merged 70-row batch definition the report is generated from                                                         |
| `seg_S1_20.jsonl` … `seg_S7_10.jsonl`     | the four per-cell segment row files that merge into it                                                                  |
| `seg_*.out`                               | each segment's scenario-runner stdout                                                                                   |
| `94_batch.out`                            | the first (interrupted) single-invocation batch attempt                                                                 |
| `pre_batch_reset.json`, `gate_reset.json` | admin `reset` output for the canonical-world gates (**not committed** — ~400 kB each of the known `gz.msgs.Pose` flood) |

The batch ran as four independently resumable per-cell segments because the WSL
VM restarted twice mid-run and killed the detached runner. Partial attempts
remain in the episode store but appear in **no** row file, so they cannot enter
the report.
