# Level C′ — 两次尝试均**判分无效**（不是任务失败）

## 设计
任务文本与 Level C 相同（**不点名文件、不给修复方向**），只增加一句"先运行一次场景看真实失败，
不要浪费轮次列目录"。目的：把 Level C 的"探索成本"问题与"诊断能力"问题分开。

## 两次尝试

| 项 | 尝试 1 | 尝试 2 |
| --- | --- | --- |
| 迭代 | 9 | 11 |
| Token | 40,310 | 40,007 |
| `run_execution` 次数 | 8 | 10 |
| `edit_file` | **0** | **0** |
| 判分结果 | **HARNESS_ERROR** | **HARNESS_ERROR** |
| `physical_tasks_dispatched` | 0 | 0 |
| 该次实验是否计入结论 | **否** | **否** |

## 为什么无效
冻结验收器的三次 Gazebo 运行全部返回 `HARNESS_ERROR`（`smoke_returncode=1`，
`physical_tasks_dispatched=0`），即仿真栈根本没跑起来。

**根因**：该 harness 原本依赖 `wsl --shutdown` 在每次判分前复位 VM；
当 pilot 在 WSL **内部**运行（本环境无 Windows Python）时没有 `wsl` 可执行文件，
VM 复位被跳过，仅靠 `pkill` 清理。agent 连续执行 8–10 次后残留状态累积，
判分阶段无法启动仿真栈。尝试 2 已加入**运行前** `pkill` 清理，仍然失败。

## 唯一可保留的观察（探索性，不作为结论）
给了"先跑一次"的指令后，agent 确实**第 1 轮就执行了场景**，但随后**反复执行 8–10 次**
（每次约 75 s，占满墙钟时间），仍然**从未编辑源码**。
这与 Level C 的"读而不写"是**不同的失败模式**：C 是探索不足，C′ 是**执行过度**。
两者都指向同一个瓶颈——**没有把"运行证据"转化为"定位"的中间步骤**。

## 结论状态：**BLOCKED（判分工具链）**
按三次规则停止该实验。要在本环境得到有效判分，必须先让 pilot 在 Windows 侧运行
（需要可用的 Windows Python，当前 `python` 是 Store 占位符），或让 harness 在 WSL 内
提供等效的 VM/状态复位（例如每次判分前重建容器或重启仿真命名空间）。
