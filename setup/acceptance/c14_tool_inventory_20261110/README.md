# C14 — 工具清单可见性对无提示定位的影响：**H0 成立（负结果）**

预注册：`docs/C14_PREREGISTRATION.md`（运行前写定判据）。

## 动机
复盘 Level C′ 发现一个未被预料的事实：该臂**拥有 `search_code`**，但 agent **一次都没调用**。
于是提出 H2：失败主因是**工具选择**（不知道有什么工具），而非"无法从证据定位"。

## 唯一改动
`SYSTEM` 提示新增**工具清单**（名称 + 一行用途）。**不**提示该用哪个工具，**不**给文件名/行号/修复方向；
任务文本与 C′ 完全一致。这符合 Level C 规则"可以告知可用工具"。

## 结果（H0 成立）
| 项 | 值 |
| --- | --- |
| 迭代 / Token | 9 / 53,045 |
| `search_code` | **0** |
| `list_dir` | **28** |
| `read_file` | 11 |
| `run_execution` | 8 |
| `edit_file` | **0** |
| 目标场景 | **ROBOT_FAILURE**（1236 行缺陷未动） |
| 回归 `normal` | PASS |
| `claim_success` / `false_success` | false / false |

## 判读（这是本轮最有价值的机制发现）
1. **工具清单不足以改变工具选择**：即使明写 `search_code` 的用途，agent 仍 0 次调用；
2. **它的默认策略是"目录遍历 + 分段读文件"**（`list_dir` 28 次），这在 1436 行文件上必然失败；
3. 这不是"看不到证据"（运行 8 次）、不是"不知道有工具"（清单可见），
   而是**在信息获取策略上缺少"先缩小范围再精读"这一步**；
4. 与 Level B 对比（点名文件 → 2/2、5–6 轮）：**提示实际上替代了搜索**。

## 对下一阶段的直接含义
下一轮最该做的不是加提示，而是**改变信息获取的界面**：
- 让失败证据**自带定位**（例如失败时输出涉及的代码区域/符号），或
- 提供一个**强制先缩小范围**的工具（如按错误码/阶段直接检索相关分支），
然后再测 Level C′——这才是"定位成本能否被工具消除"的真正检验。

## 边界
- n=1 探索性；与 Level B/C/C′ 分开统计；
- 提示改动已在代码中（`system_prompt()`），可复现。
