# Baseline v2 测量协议：把「位置」从变量里去掉

**日期：** 2026-11-11
**起因：** A-v0 的 61.1% 被位置效应污染，不是能力度量。

## A-v0 错在哪（已证实，非推测）

批次按 `T01×12, T02×12, ..., T06×12` 顺序执行，因此**模板身份与执行位置完全混淆**。

| 执行位置分位 | 通过率 | 该段模板 |
| --- | --- | --- |
| 1–18 | 100% | T01, T02 |
| 19–36 | 94% | T02, T03 |
| 37–54 | 50% | T04, T05 |
| 55–72 | 0% | T05, T06 |

两组独立证据指向负载而非模板：

1. `stack.log` 里 `set_pose rejected` 次数与判定**完全对应**——每个 `rejected>0` 的实例都失败；
   T01/T02 全部 24 个实例 `rejected=0` 且全部通过。
2. T06 放到冷机器**最前面**跑：**3/3 通过**（A-v0 里同实例 0/12）。

独立诊断给出的机制链：累积负载 → velocity-servo `pin` 超时 →
`carry_server.py:571-578` 连续 3 次 `set_pose` 失败即 `servo_abort` → PICK 阶段卡死。

## v2 改了什么（且只改这些）

| # | 改动 | 为什么 |
| --- | --- | --- |
| 1 | **随机化执行顺序**（固定种子，跑之前写进 `order.txt`） | 每个模板都经历整段机器状态分布，而不是各占一个负载区间 |
| 2 | **每实例前负载门控**：1 分钟 loadavg 回落到阈值以下、且上一个栈完全退出才开跑 | 把负载从不可控变量变成可控条件 |
| 3 | **记录每实例前后的 loadavg** | 让混淆因素**可观测**，而不是假设它不存在 |
| 4 | **分类器补上观测故障**：`pose stream is not flowing` 与 `ground_truth.errors` 非空都判 `INVALID_INFRA` | 旧分类器只查 DDS 错误，位置对照里已证实会把观测中断记成机器人失败 |

**冻结定义未动**：同一个计划构建器、同一个验收器、同一个 runner。

## 脚本

- `ci-public-window/scripts/evobot_batch_v2_gated.sh` —— A 的 v2 批次
- `ci-public-window/scripts/evobot_run_b_with_plan.sh` —— **B 的执行通路**（见下）
- `ci-public-window/scripts/evobot_baseline_b_exec.sh` —— B 的端到端驱动

> 这些脚本位于 `ci-public-window/`，**该目录不被任何 git 仓库跟踪**。
> 这是既有项目约定；本文件是唯一进版本库的记录。

## 同时补上的最大缺口：Baseline B 从未真实执行过

在此之前 B 只有「规划层正确」，**没有任何一次被独立验收器评过的真实机器人结果**。
「计划正确」永远不能当作「任务成功」。

`evobot_run_b_with_plan.sh` 与 `evobot_run_b.sh` 的 diff **只有两处**：计划来源、以及参数多一个 `$PLAN`。
其余逐字相同（起栈、派发、抓真值、独立评分）。**如果执行路径不同，A/B 差异就不再能归因给规划器。**

## 还没解决

- `geom-wire` 的 LIBERO 任务与本批次**并发**（各占 CPU）。负载已逐实例记录，可作为协变量，
  但最干净的做法是完全串行。
- 反向位置对照（T02 放最后）仍未完成——前一次尝试两次都撞上观测流中断，证据无效。
- 门控会让批次变慢（实测单实例后 load 可达 4.3，需等待回落）。这是有效测量的代价，不接受加速。
