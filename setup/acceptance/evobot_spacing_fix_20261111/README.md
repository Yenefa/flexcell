# 根因修复 > 恢复：同箱间距 0.056 → 0.090

## 上一轮留下的问题

恢复实验的分母只有 2，不足以支撑「恢复率 50%」这样的说法。
为了做大分母，用 **T13**（两物体进同一箱）造了 8 个专门实例——
这类任务**稳定触发执行层占用冲突**，正是恢复该处理的场景。

## 第一次跑：恢复 0/4

| task | a1 | a2 | 结果 |
| --- | --- | --- | --- |
| 4 个实例 | `err 61` | `err 60` | 全部失败 |

### 归因（4 例完全相同）
```
plan: box_a -> (0.222, 0.05),  box_b -> (0.278, 0.05)   间距 0.056
attempt1 后实测: box_a = (0.229, 0.05)   ← 漂移 +7mm
attempt2 (resume) -> err 60 declared destination occupied
有效间距 = 0.278 - 0.229 = 0.049 m  <  clearance 0.050 m
```

**间距只比 clearance 多 6 mm，实测漂移 ~7-10 mm 就吃掉了余量。**
resume 重建计划完全正确，但目标点本身物理上就冲突——恢复无解。

## 修根因：间距改为 0.090

| 参数 | 值 | 是否改动 |
| --- | --- | --- |
| clearance 契约 | 0.050 m | **未动** |
| 箱半径 | 0.060 m | **未动** |
| **落点间距** | **0.056 → 0.090 m** | **改（加大间距）** |

0.090 相对 clearance 留 40 mm 余量（>2× 实测漂移），
偏移 ±45 mm 仍在 60 mm 箱半径内。**这是加大间距，不是放宽阈值。**

新增两条测试：
- `SPREAD_STEP_M > clearance + 漂移`；
- 偏移必须在箱半径内。

## 修复后：8/8 首试成功，恢复路径一次都没触发

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 首试成功 | 4/8 | **8/8** |
| 需要恢复 | 4 | **0** |
| 最终通过 | 4/8 = 50% | **8/8 = 100%** |
| False Success Rate | 0/8 | **0/8** |

## 这一轮真正的结论

**对这类失败，修根因比建恢复更有效。**

恢复机制是对的（上轮确实救回 1 例 `err 62`），但它处理的是**症状**；
当失败来自「落点间距不足」这种可计算的设计错误时，
**应该先修间距，而不是让恢复去兜底**。

两个数字放一起看很清楚：
- 建恢复：0/4 被救回；
- 修间距：4/4 不再需要救。

## 同时修掉的另一个真实缺陷

0.090 间距下 **3 个物体物理上放不进 60 mm 箱**。原代码会抛通用错误；
改为**明确拒绝**并说明原因（「既满足 clearance 间距又放进箱内是不可能的」），
而不是悄悄压缩间距生成一个「看起来合法、上机器人必失败」的计划。

当前场景只有 2 个物体，所以不影响已测任务；但这是必须挡住的未来陷阱。
