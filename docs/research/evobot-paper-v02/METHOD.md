# 方法：测量仪器，不是结果

> **状态：DRAFT。本文件不包含任何实验结果。**
> 24 个槽位全部 `NOT_RUN`，6 个保留场景未执行。写在这里的是**仪器怎么造、为什么这么造**，

## 1. 要回答的问题

同一缺陷、同一评估器、同一容差、同一模型、同一预算下，**改变「给修复者看什么」**，修复成功率会怎么变。

四个条件（PROTOCOL.md §2）：

| 条件 | 名称 | 修复者能看到 | 用来分离什么 |
| --- | --- | --- | --- |
| A | 无反馈 | 只有任务目标与可改字段 | 基线：纯靠目标文本能不能修对 |
| B | 真实执行反馈 | 本 run 的阶段、错误码、观测值、日志子集 | 反馈本身的价值 |
| C | 失配反馈 | 与 B 同结构，内容来自**另一条预登记的 run** | 反馈的**相关性**是否必要 |
| D | 真实反馈 + 显式指导 | B + 预先写定的行动指令 | 结构之外的直接指导 |

C 是整个设计的支点：如果「看起来像反馈、但其实来自别处」与真反馈效果相近，那么「有反馈就有用」这个直觉就是错的。C 的 donor 在运行前绑定进 manifest，不得临场挑选。

## 2. 三个域，以及为什么边界要由机器强制

| 域 | 内容 | 谁能改 |
| --- | --- | --- |
| 开发技能 | 修复动作本身 | 修复者，且仅限契约列出的字段 |
| 执行技能 | 运行时接口 | 不可改 |
| 物理能力研发 | 真机/仿真能力 | 不在本实验范围内 |

边界不是靠约定，而是 `config/skill_boundaries.json` 里三条被脚本检查的规则（`execution_without_development`、`runtime_uses_execution_interfaces`、`physical_core_without_execution`）。理由很实际：一个只在文档里存在的边界，会在第一次有人赶时间的时候消失。

## 3. 冻结的判据（`benchmark/repair_eval/contracts`）

判定所用的目标、物体、容差、保护文件摘要**全部来自冻结契约**，不来自候选的自述。

- 契约是确定性 JSON，`sha256()` 进每一条运行记录；
- 候选只能声明「我改了什么」，不能声明「目标是什么」——重述不可变字段判 `TAMPERED_IMMUTABLE`；
- 判定三态：`ACCEPT` / `REJECT` / `UNKNOWN`。**`UNKNOWN` 永不升级为 `ACCEPT`**，且有一条内部不变量：任何失败的检查若没带理由码，状态强制降为 `UNKNOWN`，使 bug 无法造出 `ACCEPT`；
- 证据摘要在本层是**声明值**，不是校验值（只验格式与齐全度，不重算）。真实摘要由采集器在跑完后重算。

负例语料 6 类 + 正例 1 个，分别统计错误接纳与错误拒绝。目前 **0 / 0 / 7 例**——这证明判定逻辑不误纳，不证明机器人完成了抓放。

## 4. 信息边界的实现（`benchmark/repair_eval/visibility.py`）

- 三个根（候选 / 裁决 / 隐藏答案）构造期校验互不包含；重叠即拒。
- 保留名（`verdict.json`、`result.json` 等）按规范化路径判定，别名、`..`、绝对路径、软链、硬链各自有独立理由码。
- **评估器源码 `gate/` 在四个条件下一致封印**（`sealed_material`）：读到 `PASS_IF` 阈值就能照阈值调参，那是改尺子。封印只在工具门面层——文件仍在候选目录里供验收子进程执行，绕过门面的代码照样能读。措辞必须按这个强度写。
- 新 run 先过 `assert_fresh_run()`：候选里残留上一次的裁决或遥测即 `StaleArtifact`（fail-closed）。代价是所有产物必须在读反馈**之前**生成——这个顺序在实现时踩过一次。

## 5. 预算与账本（`experiments/repair_eval_v02/budget.py`）

每条候选 ≤ **6 次模型交互 / 20,000 tokens**。两道上限都在**调用前**检查，所以会超的那次调用根本不发出；token 只能在调用后知道，故调用后再查一次，且那次的成本仍然计入。任一上限触发即**永久关闭**账本——协议禁止「再给一次机会」。

耗尽记 `BUDGET_EXHAUSTED`，**不算成功**：一次超预算跑完仍记成成功，会系统性地偏向话多的那个条件。

## 6. 记录与分母

运行记录字段由 `DATA_DICTIONARY.md` §3.3–§3.6 声明，代码**解析该文档**做一致性检查（文档加字段则测试红，代码发明字段也红）。摘要在文本上按 `utf8-lf-sha256/1` 归一换行，否则同一份反馈在 Windows 与 Linux 上会得到两个不可比的数字。

分母口径（DATA_DICTIONARY §4）：`SUCCESS_VERIFIED` 进分子；`FAIL` / `BUDGET_EXHAUSTED` 进分母；`UNKNOWN` 单列；`INVALID` 不进任何分母但**必须出现**在表里。

`false_accept` 由代码从各道门推导，不接受调用方声明；`NOT_RUN` 的门算作「未通过」——没跑过的门不算通过，否则未测量的运行会被算成真阳性。`false_reject` 永不由代码推断，文档要求人工复核后才可置 true。

手写的 `RUN_MANIFEST.md` 状态列与记录之间由 `reconcile.py` 对账；试运行记录（`DRY_RUN` / `SCRIPTED`）**一律排除**，永远不能提升槽位——否则「没跑过」到「跑过」的痕迹会消失。

## 7. 保留场景的纪律（`holdout.py`）

2 个未参与开发的布局 × 3 个预定初态 = 6 个槽位。候选必须**先冻结**再评估，且**结果时间戳不得早于冻结时间**：冻结晚于某条结果，意味着候选可能是照着那条结果挑的，再怎么解释都救不回来。失败的槽位一次写入，不能被改写——补跑是新记录，不是覆盖。

## 8. 这套方法**不能**支持什么

- 不能支持任何成功率数字：24 槽 `NOT_RUN`，6 保留场景未执行。
- 不能支持跨本体或真机泛化：全部离线，合成夹具。
- 不能支持统计显著性：每格 n=3，只写 `x/3`，不写百分数。
- 不能替代独立评估器：契约层判「是否满足声明」，不判「测量是否真实」。
- 历史 W5 记录不进任何 v0.2 分母，也不作为分子。
