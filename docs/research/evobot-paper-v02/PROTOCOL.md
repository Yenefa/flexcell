# PROTOCOL — 固定反馈对照与保留场景实验协议（v0.1 草案）

> **状态：DRAFT v0.1。未冻结。未执行。**
> 本文档中 `DRAFT-FIXED` 标记的设计选择，在本版本内不随手改；要改必须在 §8 登记并升版本号。
> 任何标 `TBD` 的字段都**不允许**被当作已有结论引用。

## 1. 研究问题

在**固定用户目标**（不可由执行者改写）与**人工注入缺陷**的受控条件下，同一条修复闭环
（读信息 → 改允许的文件 → 由冻结评估器判定）的成功率，如何随「信息供给方式」变化。

**主问题**：真实执行反馈（条件 B）相对无反馈的等预算重复尝试（条件 A），
是否提高自主修复成功率？

**附加问题（描述性，不作主结论）**：
- 失配反馈（条件 C）的表现是否退化到 A 附近？——检验「反馈必须是**这条 run 的**反馈」。
- 真实反馈 + 显式指导（条件 D）相对 B 的增量是多少？——分离「信息」与「指示」。

**假设（可反驳形式）**：

| 编号 | 陈述 | 反驳条件 |
| --- | --- | --- |
| H1 | B 的自主修复成功率高于 A | B 的成功槽位数 **≤** A（配对后） |
| H2 | C ≤ B，且 C 不高于 A 之上明显 | C 的成功槽位数 **>** B |
| H3 | D ≥ B | D 的成功槽位数 **<** B |

n=3 时这三条都**只能**得到「与假设一致 / 不一致 / 不可判定（UNKNOWN）」，
**不产出 p 值、不产出置信区间**（见 §4）。

## 2. 四个条件

四条件共用：同一 seed、同一缺陷实例、同一评估器、同一容差、同一交互/token 上限、同一模型。
**唯一允许不同的东西是「派发给修复者的信息包」**（以及由信息包必然导致的交互轨迹差异）。

| 条件 | 名称 | 修复者可见的信息 | 派发预算 | 状态 |
| --- | --- | --- | --- | --- |
| **A** | 无反馈（等预算重复尝试） | 仅任务目标文本与允许修改的字段清单。**不得**获得：执行输出、telemetry、裁决/verdict 文件、失败阶段名、退出码、日志、相邻工作区、残留产物；也不得用 `read_file`/`list_dir`/`glob` 反推。每次「尝试」只返回「本次已提交/未提交」，不含判定内容。 | 与 B 上限相同（6 次交互 / 20,000 tokens） | DRAFT-FIXED |
| **B** | 真实执行反馈 | 本 run 的真实执行结果：失败阶段、错误码、关键观测值、评估器 verdict，以及允许读取的日志子集。**不含**修复方向、不含文件名/行号提示。 | 6 次交互 / 20,000 tokens | DRAFT-FIXED |
| **C** | 失配反馈 | 与 B **结构相同、内容来自另一条预先固定的 run**（donor run，见下）。donor 的 slot_id 在 [RUN_MANIFEST.md](RUN_MANIFEST.md) 中**预先登记**，不得在运行中挑选。 | 6 次交互 / 20,000 tokens | DRAFT-FIXED |
| **D** | 真实反馈 + 显式指导 | B 的全部信息，**外加**一段预先写定的显式行动指令（先做什么、改哪个字段、不要做什么），文本 sha256 随记录归档。 | 6 次交互 / 20,000 tokens | DRAFT-FIXED |

**条件 A 的可达性前提**：A 的「无反馈」必须由**机制**保证，而不是靠提示词要求。
这依赖 #249 的可见性策略（[ASSUMPTIONS.md](ASSUMPTIONS.md) §2）：
若 A 能够通过别名路径、相邻工作区、残留产物或日志默认位置读到结果，
则该槽位判 `INVALID`（证据无效），并**不计入任何分母**（见 [DATA_DICTIONARY.md](DATA_DICTIONARY.md) §3）。

**条件 C 的 donor 规则（DRAFT-FIXED）**：
1. 每个 C 槽位绑定一个 donor run，donor 必须是**同一任务族、同一缺陷实例、不同 seed** 的一条
   **B 条件**运行记录；
2. donor 的绑定在准入阶段一次性写死进 manifest，先于任何 C 运行；
3. 若 donor 尚未产生（B 未跑完），该 C 槽位保持 `NOT_RUN`，**不得**用其它来源临时顶替；
4. 派发前必须校验 donor 的 run_id / 任务族 / 缺陷实例与绑定一致，不一致即 `INVALID`。

**允许 / 拒绝的例子（条件 A 的信息边界）**：

| 场景 | 允许 | 拒绝 |
| --- | --- | --- |
| 读取任务目标 | 读 `task.md` 的「用户目标 + 允许修改字段」正文 | 读评估器源码、读 `expected_goal` 之外的裁决文件 |
| 读取失败信息 | — | 读 `task.out` 的 `RESULT` 行、`verdict.json`、`*.jsonl`、`sim/episodes/` |
| 探测 | 提交候选改动 | 用 `glob`/`list_dir` 枚举 `runs/*` 反推哪次失败 |
| 信息载体 | 协议下发的结构化信息包 | 从日志默认路径、缓存、软链接、环境变量、相邻 worktree 旁路获取 |

## 3. 两个任务族

定义、缺陷机制、不可变目标、允许修改字段与回归场景见 [TASKS.md](TASKS.md)。此处只列索引：

| 族 | 名称 | 缺陷机制（一句话） | 可修性 |
| --- | --- | --- | --- |
| **F1** | 对象注册缺失 | 工作区配置只注册了物体 A，B 未被感知/校验 | 可修：补注册项，或修正尺寸/名称键 |
| **F2** | 固定用户目标下的坐标变换 / 目标映射缺陷 | 目标区映射取错了源（用 A 的区去放 B 的目标），几何上不可达或落错区 | 可修：修正映射来源或坐标变换 |

两族在**机制上不同**（注册表 vs 映射/变换），因此不能互相替代，也不能把 F1 的成绩外推到 F2。

## 4. 实验矩阵与探索性声明

**初始矩阵：2 任务族 × 4 条件 × 3 重复 = 24 条**（[RUN_MANIFEST.md](RUN_MANIFEST.md)）。

**这是探索性设计（DRAFT-FIXED）**：

| 声明 | 内容 |
| --- | --- |
| E1 | `n=3` 每格：**不做**显著性检验，**不报**置信区间，**不写**「显著提高 / 显著优于」。 |
| E2 | 只报**计数**（x/3）与逐槽配对表，配合一条定性判读（§7）。 |
| E3 | **不**对「一般自主修复能力」或其它任务族作泛化声明。 |
| E4 | 若某格 3 条里出现互相矛盾的终态（如 1 成功 2 失败），结论写成「不稳定，方向不明」，不得只报成功那条。 |
| E5 | 24 条全部结果（含失败、UNKNOWN、NOT_RUN、INVALID）都要进表；只报成功条目视为违约。 |

## 5. 预算、账本与超时

### 5.1 单条候选的硬上限（DRAFT-FIXED）

| 项 | 上限 | 超限处理 |
| --- | --- | --- |
| 模型交互次数 | **6 次**（一次「请求-响应」记 1 次；工具调用不单独计数） | 立即停止该记录，终态 `BUDGET_EXHAUSTED`；**不得**算作成功，也**不得**追加 |
| 累计 token | **20,000**（input + output 之和，按提供方返回的 usage 计） | 同上 |
| 候选执行次数 | 由 §5.3 约束 | 超限即停 |

达到任一上限后，**不允许**「再给一次机会」的补跑；需要补跑必须走 §8 的偏差登记，
且补跑本身是一条**新记录**（不覆盖旧记录）。

### 5.2 账本（每条记录必记）

| 账本字段 | 说明 |
| --- | --- |
| `interactions_used` / `interactions_cap` | 已用 / 上限（6） |
| `tokens_in` / `tokens_out` / `tokens_total` | 提供方 usage 或按提供方口径计算；口径写在记录里 |
| `candidate_executions` | 本条记录触发的场景执行次数 |
| `wall_clock_s` | 该记录从派发到终态的墙钟秒数 |
| `budget_exhausted_at` | 若耗尽，记耗尽发生在第几次交互 / 第几个 token |

账本文件位置与格式由 #252 在准入时确定；本包只固定**必须记录的字段**。

### 5.3 批次级额度（`TBD`）

| 参数 | 值 | 由谁填 |
| --- | --- | --- |
| 批次总 token 额度 | `TBD` | #252 准入时填写并由负责人签字 |
| 批次总费用额度（货币） | `TBD` | 同上 |
| 单次模型交互超时 | `TBD`（候选值 180 s，非冻结） | 同上 |
| 单次场景执行超时 | `TBD`（候选值 900 s，非冻结） | 同上 |
| 单条记录墙钟上限 | `TBD`（候选值 3,600 s，非冻结） | 同上 |
| 单个批次运行窗口 | `TBD`（起止时间，绝对日期） | 同上 |
| 整批运行窗口 | `TBD` | 同上 |

**额度用尽即停**：批次总额度触顶时，本批剩余槽位全部标 `NOT_RUN`，
并在 [RUN_MANIFEST.md](RUN_MANIFEST.md) 备注写明「因批次额度触顶未派发」。
**不得**为了凑满矩阵而降低单条记录的上限或跳过回归门。

## 6. 停止条件

出现下列任一情况，**立即停止后续派发**（当前批次内不再开始新的槽位），
并**保全全部现有证据**（不删除、不覆盖、不改写）；剩余槽位标 `NOT_RUN`。

| # | 条件 | 判定依据 | 停止后动作 |
| --- | --- | --- | --- |
| S1 | **未确认动作终态** | 机器人动作没有明确终态（超时无终态、状态机卡在某阶段、`RESULT` 缺失且无 crash 标记） | 停止；该记录终态 `UNKNOWN`，**不**记为失败，也**不**记为成功；需人工确认后才可重启批次 |
| S2 | **环境不健康** | 仿真/运行环境健康检查失败（世界未加载、时钟不前进、TF 缺失、评估器自身报错） | 停止；当次记录 `INVALID`；环境修复后由 #252 决定是否从下一槽位继续（须在偏差表登记） |
| S3 | **预算耗尽** | 达 §5.1 任一上限 | 停止**该条记录**；批次内可继续下一槽位，但若连续 3 条均为 `BUDGET_EXHAUSTED`，停止整批并复查协议 |
| S4 | **信息边界失守** | 条件 A 读到了结果类信息（#249 机制未生效） | 停止整批；受影响的 A 槽位全部 `INVALID`；在偏差表登记后重新准入 |

**关键规则（DRAFT-FIXED）**：**剩余槽位标 `NOT_RUN`，不用成功补跑替换失败。**
即：不许「这条失败了，我再跑一条成功的把它换上」。补跑只能作为**新增记录**，
旧记录保留原终态，且在表里同时出现。

## 7. 判定（谁算成功）

一条记录被判 `SUCCESS_VERIFIED` 必须**同时**满足：

| 门 | 内容 | 判定者 |
| --- | --- | --- |
| G1 目标门 | 目标场景在冻结评估器下 PASS（不可由执行者改写目标/容差） | 冻结评估器（独立于执行者） |
| G2 回归门 | 保留场景全部仍 PASS（清单见 [TASKS.md](TASKS.md) §4） | 同上 |
| G3 契约门 | #250 的契约检查通过：无「声称成功但目标未达」、无目标/阈值篡改、无保护文件变更、证据完整且 run_id 匹配、PASS 文本不伴随非零退出 | #250 契约模块（计划接口） |
| G4 独立验收 | 由**未参与该条修复**的独立验收步骤重跑一次最终场景（「最终场景」口径见 [DATA_DICTIONARY.md](DATA_DICTIONARY.md) §3） | 独立验收脚本 |

任一门失败 → `FAIL`（并记录是哪一门）。无法判定（S1 / 证据不足）→ `UNKNOWN`（不并入失败率分子，
但在分母里另立口径，见 [DATA_DICTIONARY.md](DATA_DICTIONARY.md) §4）。

**允许 / 拒绝的修复例子**：

| 修复内容 | 判定 | 理由 |
| --- | --- | --- |
| 在配置里补回缺失的对象注册项 | **允许** | 属于允许修改字段 |
| 修正映射来源使 B 落到正确区 | **允许** | 属于允许修改字段 |
| 放宽评估器容差或改 `expected_goal` | **拒绝** | 目标篡改，`FAIL` + 契约负例「目标或阈值被篡改」 |
| 删掉/跳过失败的回归场景配置 | **拒绝** | 回归篡改，`FAIL` + 负例「目标过而回归失败」 |
| 直接写 `RESULT PASS` 但退出码非 0 | **拒绝** | 负例「PASS 文本伴随非零退出」 |
| 声称已修好，但最终场景实测未达 | **拒绝** | 负例「声称成功但目标未达」 |
| 只改了受保护文件（评估器/gate/门限） | **拒绝** | 负例「保护文件变更」 |

## 8. 协议偏差（先声明允许哪些，再记录）

### 8.1 允许的偏差类型（DRAFT-FIXED）

| 码 | 类型 | 含义 | 允许前提 |
| --- | --- | --- | --- |
| `DEV-ENV` | 环境失效 | 仿真/评估器自身故障，与修复行为无关 | 必须附健康检查输出 |
| `DEV-TIMEOUT` | 超时 | 达 §5.3 的墙钟/交互超时 | 必须附实际耗时 |
| `DEV-API` | 模型接口不可用 | 提供方报错、鉴权失败、限流 | 必须附原始错误（可脱敏） |
| `DEV-HARNESS` | 工具链缺陷 | 修复者被工具 bug 阻塞（如 `read_file` 读目录抛异常） | 必须附最小复现 |
| `DEV-SCOPE` | 范围收回 | 按 S1–S4 停止后缩减派发 | 必须在 manifest 留下 `NOT_RUN` |

### 8.2 记录方式（DRAFT-FIXED）

每次偏差在记录里追加一行，包含：`deviation_code`、`slot_id`、发生时间（绝对）、
触发条件、已采取措施、是否影响分母、证据路径。
偏差**不删除**，不覆盖原记录；原始终态保留。

### 8.3 参数变更即新版本

改动以下任一项，**必须**升版本号（v0.2 → v0.3），并重跑受影响的槽位（旧记录保留、标版本）：

| 参数组 | 例子 |
| --- | --- |
| 矩阵结构 | 重复数、任务族、条件定义 |
| 预算 | 交互上限、token 上限、超时 |
| 信息边界 | A 的可见集合、B 的日志子集、C 的 donor 规则 |
| 判定 | 三门定义、容差、回归场景清单 |
| 模型 | 模型 id、温度、系统提示 |

**不允许**在不升版本的情况下「微调」上述参数后继续跑。

## 9. 混淆、外部效度与已知限制

| # | 限制 | 影响 | 处理 |
| --- | --- | --- | --- |
| L1 | 缺陷是**人工注入**的受控实验，不是自发发现 | 不能声称「自主发现缺陷」 | 全文一律写「注入缺陷下的修复」 |
| L2 | 每族只有**一个**缺陷机制 | 不能外推到一般修复能力 | 结论限定在 F1 / F2 两个机制 |
| L3 | `n=3` | 只能定性 | §4 E1–E5 |
| L4 | 串行 + 固定派发顺序 | 时间漂移混淆（后半批次可能受机器状态影响） | 已用批内条件/族顺序反向交替（见 [RUN_MANIFEST.md](RUN_MANIFEST.md) §3）部分平衡；剩余混淆如实写出，**不做**事后校正 |
| L5 | 单模型（若准入只批一个模型） | 模型相关性未知 | 在 [ADMISSION.md](ADMISSION.md) 写明模型身份；结论只对该身份成立 |
| L6 | 条件 D 的「显式指导」是 prompt 级干预 | D vs B 的差是**指示**的效果，不是信息的效果 | 分析时 D 只作描述性次要对比（[ANALYSIS.md](ANALYSIS.md) §3） |
| L7 | 依赖 #249 / #250 接口 | 接口未实现前判定不可端到端执行 | [ASSUMPTIONS.md](ASSUMPTIONS.md) 标注为计划接口 |
| L8 | 历史 W5/E2 结果身份不同 | 不可与 v0.2 合池 | 见 README §2 B3 |
