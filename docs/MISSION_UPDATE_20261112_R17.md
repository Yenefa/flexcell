## §19.2 洞一：校验器不验任何数字

`evidence_strings()` 只保留 8 字符以上的字符串，**所有数字被跳过**。后果：

> 把 `error_code 99` 喂进去照样通过。`ec 61` 和 `60` 是区分那两条记录的唯一信息，而它是**未经校验的**。
> 它们是对的，是因为写的人诚实，不是因为检查确认了它。

**用子串搜索修不好**：`60` 会出现在时间戳、坐标、端口里。所以数字和布尔事实改为**结构化校验**——
必须在**解析后的 JSON 对象**里匹配一个**带类型的字段值**；`_matches` 还拒绝把布尔当整数。

测试 **11/11**，其中两条直接来自审核者自己的破坏实验：

| 用例 | 期望 | 结果 |
| --- | --- | --- |
| `error_code 99`（真实是 60） | REJECT | **REJECT** |
| `error_code 0` 只作为 `60` 的子串存在 | REJECT | **REJECT** |

第二条证明检查是**结构的，不是文本的**。

**有一条旧测试必须改前提**：「证据全是数字 → 拒绝」断言的是**旧的错误行为**。数字现在可校验，
所以过时的是它的**前提**，不是它的期望。

对六条真实记录：2 条真实证据的**带着 error code 一起通过**，4 条遗留的仍然失败。

## §19.3 洞二：审核对检索是「可选的」

审核者最锋利的一句：

> 证据校验失败的记录会被丢掉；**证据校验通过但教了错课**的记录，会被**检索并执行**。

第 15 轮只修了一半：REJECT 现在能挡住 lesson，但**没有任何判决**的记录**照样能被检索**——
**这正是第 14 轮那两条错误 lesson 在被人审核之前穿过的窗口**。

现在：**一条记录必须有明确的独立 `ACCEPT` 才能影响计划。** 没有判决 = 没有批准，不是「疑罪从无」。

```
no review ledger -> NOT retrieved                    PASS
independent ACCEPT -> retrieved                      PASS
independent REJECT -> NOT retrieved                  PASS
ACCEPT for another digest -> NOT retrieved           PASS
corrupt ledger -> NOT retrieved (fail closed)        PASS

5/5 tests passed
```

最后两条是关键：**记在别的记录摘要上的 ACCEPT 不能批准这一条**；**损坏的 ledger 必须 fail closed**。
**一个解析出错就放行的审核闸门不是闸门。**

效果：**所有模板检索结果都是 0 条 lesson**。这是正确的——两条已验证记录都被独立拒绝——
而且现在是**被强制**的，不只是恰好如此。
