# Acceptance interface

What the three task-level actions expose, what their fields mean, and how one run is
judged. Everything below was read from the source on 2026-11-18; file and line
references are given inline and indexed by claim in §8.

Scope: **simulation only**. This document defines an interface, not a result. It makes
no success-rate claim.

## 1. Action names (exact)

| Action type | Server node | Action name | Declared in |
| --- | --- | --- | --- |
| `RunPickPlace` | `task_fsm_server` | `/run_pick_place` | `task_fsm_server.py:198` |
| `RunDemo` | `task_fsm_server` | `/run_demo` | `task_fsm_server.py:295` |
| `VerifyObject` | `verify_server` | `/verify_object` | `verify_server.py:41` |

There is **no `/task` action**. The single-object task is `/run_pick_place`. The
`w1_client.py --action task` spelling only selects that client's `RunPickPlace` entry
(`w1_client.py:31`); it is not an action name. Likewise `/verify_object` is the
action; the server node is `verify_server`.

Both task actions share one arm lease: a second goal while one is running is refused
with `ERR_RESOURCE_BUSY` (`task_fsm_server.py:1012-1015`).

## 2. Goals

### `RunPickPlace` — `/run_pick_place`

| Field | Type | Meaning |
| --- | --- | --- |
| `object_name` | `string` | Object to move. Empty string is rejected with `ERR_OBJECT_UNKNOWN` (`task_fsm_server.py:1024-1026`). |
| `place_pose` | `geometry_msgs/PoseStamped` | Destination in the world frame. Only `place_pose.pose.position` is read; the header is ignored (`task_fsm_server.py:906-907`). |
| `motion_profile_id` | `string` | Motion profile. Empty falls back to `demo_slow` (`task_fsm_server.py:1040-1041`). |
| `skip_verify` | `bool` | Skips the VERIFY stage. **This makes success unmeasured** — see §4.3. |

### `RunDemo` — `/run_demo`

| Field | Type | Meaning |
| --- | --- | --- |
| `scenario_id` | `string` | Free-form tag. Empty falls back to `week1_demo_v1` (`task_fsm_server.py:900-901`). |

Objects and zones are **not** in the goal. They come from the server parameters
`object_a` / `object_b` and `zone_1_*` / `zone_2_*` (`task_fsm_server.py:205-212`);
`src/flexcell/flexcell_skills/config/week1.yaml` sets
`target_box_a -> zone_1 (0.12, -0.15, 0.0175)` and
`target_box_b -> zone_2 (0.25, 0.05, 0.0175)`.

Sequence per run (`RunDemo.action:1-6`): `OBSERVE_A -> PICK_A -> PLACE_A -> VERIFY_A
-> OBSERVE_B -> PICK_B -> PLACE_B -> VERIFY_B`. Recovery is bounded by
`recovery_budget` (default 1): a recoverable failure gets `REOBSERVE` plus one retry.

### `VerifyObject` — `/verify_object`

| Field | Type | Meaning |
| --- | --- | --- |
| `object_name` | `string` | Object to measure. |
| `expected_pose` | `geometry_msgs/Pose` | Expected pose in the world frame (unquoted `Pose`, not `PoseStamped`). |
| `position_tolerance_m` | `float64` | `0` means "use the server default", `default_tolerance_m` = 0.05 m (`verify_server.py:31, 95`). |

## 3. Results

### `RunPickPlace.Result`

| Field | Type | Meaning |
| --- | --- | --- |
| `outcome` | `uint8` | `0` SUCCEEDED, `1` FAILED, `2` CANCELED. |
| `error_code` | `uint16` | `0` NONE, `21` OBJECT_NOT_FOUND, `32` CANCELED, `41` RESOURCE_BUSY, `50` SKILL_FAILED, `51` RECOVERY_EXHAUSTED, `52` SKILL_CONTRACT_VIOLATION, `53` SAFETY_REJECTED. |
| `fsm_trace` | `string[]` | Ordered state names, e.g. `OBSERVE_A`, `PICK_A(attempt=1):OK`, `PLACE_A:OK`, `VERIFY_A(attempt=1):OK`. |
| `object_at_place` | `bool` | `true` iff the matching VERIFY result was `OUTCOME_VERIFIED` (`task_fsm_server.py:958-963`). With `skip_verify=true` it is faked from PLACE — see §4.3. |
| `residual_carry` | `bool` | `true` when the task was canceled while carry was still engaged; the arm is not safe to reuse until reset. |
| `carry_state_unknown` | `bool` | `true` when a cancel could not read `/flexcell/carry_snapshot`; treated as unsafe, not as `IDLE`. |
| `final_position_error_m` | `float64` | `VerifyObject.position_error_m` of the last verify; `NaN` when no measured pose exists. |
| `evidence_id` | `string` | Task-level evidence id, `<scenario>-<8 hex>` (`common.py:325-327`). |
| `detail` | `string` | Human-readable terminal reason. |
| feedback | — | `{string state, uint32 elapsed_ms}` only. |

`outcome == SUCCEEDED` means every assignment reached `outcome == 0` in a VERIFY
result; completion is structural, not a policy opinion (`task_fsm_server.py:1078-1088`).

### `RunDemo.Result`

| Field | Type | Meaning |
| --- | --- | --- |
| `outcome` | `uint8` | As above. |
| `error_code` | `uint16` | Same code set as `RunPickPlace`, minus `ERR_OBJECT_UNKNOWN` (`RunDemo.action:13-19`). |
| `scenario_id` | `string` | Echo of the resolved scenario tag. |
| `run_id` | `string` | `<scenario>-<8 hex>`, generated by the server (`task_fsm_server.py:908`). Distinct from `evidence_id`. |
| `fsm_trace` | `string[]` | As above, e.g. `PICK_B(attempt=1):FAIL:ERR_GRASP_FAILED`, `RECOVERY:REOBSERVE+RETRY`. |
| `object_a_at_zone` | `bool` | `true` iff the `VERIFY_A` result was `OUTCOME_VERIFIED` (`task_fsm_server.py:968-979`). |
| `object_b_at_zone` | `bool` | Same for B. |
| `residual_carry` | `bool` | `true` when cancelled while carry was still engaged; do not start another task until reset. |
| `carry_state_unknown` | `bool` | `true` when the cancel cleanup could not read carry state; treat as unsafe. |
| `zone_a_error_m` | `float64` | `VERIFY_A.position_error_m`; `NaN` if unmeasured. |
| `zone_b_error_m` | `float64` | Same for B. |
| `duration_s` | `float64` | Monotonic wall time for the whole run. |
| `evidence_id` | `string` | Task-level evidence id. |
| `detail` | `string` | Terminal reason. |
| feedback | — | `{string state, uint32 elapsed_ms}` only. |

### `VerifyObject.Result`

| Field | Type | Meaning |
| --- | --- | --- |
| `outcome` | `uint8` | `0` VERIFIED, `1` MISMATCH, `2` FAILED, `3` CANCELED. |
| `error_code` | `uint16` | `0` NONE, `2` INTERNAL, `21` OBJECT_UNKNOWN, `22` WORLD_STATE_UNAVAILABLE, `32` CANCELED. |
| `status` | `uint8` | Derived from `outcome`: `0` NONE, `1` SUCCESS, `2` FAILURE, `3` SKIPPED, `4` CANCELED. VERIFY maps `0 -> 1`, `3 -> 4`, and both `1` and `2` to `2` (`contracts/error_codes.py:179-184`). |
| `verified` | `bool` | `position_error_m <= tolerance`. |
| `measured_pose` | `geometry_msgs/Pose` | Measured pose. Only meaningful when `has_measured_pose` is true. |
| `has_measured_pose` | `bool` | False when the pose stream had no fresh sample. |
| `position_error_m` | `float64` | Euclidean distance between measured and expected position. |
| `evidence_id` | `string` | Measurement evidence id. |
| `detail` | `string` | Includes the tolerance and the actual error. |
| feedback | — | `{uint32 elapsed_ms}` **only**; this action publishes no state feedback. |

Two semantics that matter to a client:

1. **MISMATCH is a successful measurement.** `outcome=1` reports that the object is
   outside tolerance; the goal is still finished with `succeed()`
   (`verify_server.py:108-113`), so the action result is delivered normally and
   `status=2`. Do not read `status == 2` as "the action failed".
2. **CANCELED means the cancel was seen before the measurement.** The check is the
   first thing the execute callback does (`verify_server.py:84-86`), and the outcome
   constant is documented as "cancel requested before the measurement"
   (`VerifyObject.action:9`).

A missing sample — including a dead pose stream — is reported as
`ERR_OBJECT_UNKNOWN (21)` on this path (`verify_server.py:87-89`).
`ERR_WORLD_STATE_UNAVAILABLE (22)` is declared in the interface and used by the
observe/pick servers, but the current verify server does not emit it.

## 4. What "independent acceptance" means here

### 4.1 The measurement is the simulator's ground truth

`VerifyObject` calls `sample_gz_pose(object_name)` (`verify_server.py:87`), which
reads the live Gazebo `Pose_V` stream and rejects samples older than 1 s
(`common.py:243-266`). The number it returns is the simulator's model pose, not a
value produced by the policy, the planner or the agent.

The server's own docstring states the doctrine: *"Success is measured, never
inherited"* (`verify_server.py:4-5`).

### 4.2 The agent's self-report is not evidence

`outcome == 0` and `object_at_place == true` are claims made by the same process that
did the work. They are useful as a routing signal, not as proof. In this repo the
failure mode is documented: a PLACE "ghost success" passed every self-reported gate
(`setup/92_referee.py:1-10`), which is why the referee recomputes the headline values
outside the servers, and why `docs/EVALUATION_METRICS.md:24-30` separates
`outcome=0` from `passed=true` and requires `false_success == 0`.

Acceptance therefore re-derives the verdict from:

- the **measurement** (`VerifyObject.position_error_m`, or the same value recorded in
  `verify.jsonl`), and
- the **raw ground-truth pose** when a second opinion is needed
  (`setup/92_referee.py` is the existing referee; `scripts/accept_run.py` is the
  per-run wrapper, §6).

A claim with no measurement is not a pass. That includes a run where the agent
reported success but `skills/verify.jsonl` has no parseable measurement, or the action
result has no `has_measured_pose`.

### 4.3 `skip_verify` is not acceptable evidence

With `skip_verify=true`, the server sets `object_at_place=true` from
`PLACE.outcome == SUCCEEDED`, and `final_position_error_m=NaN`
(`task_fsm_server.py:958-963`). That is a self-report path by construction. Acceptance
runs must use `skip_verify=false`.

### 4.4 The independence has a boundary

`VerifyObject` is independent of the **agent**; it is not independent of the
**simulator**. Ground truth is whatever Gazebo reports, so model/plugin faults,
detachable-joint artifacts and world-file drift are all inside the measurement. This
is why the boundary in §7 says "simulation only".

### 4.5 What counts as PASS

A run passes when the typed task result **agrees with at least one independent
measurement**, and any second measurement agrees with the first. The checks are
mechanical and live in `scripts/accept_run.py` (§6); this section states the rule, §6
states what the tool actually reads.

1. the runner's `result.json` has `status == "PASS"`;
2. `task.outcome == "OUTCOME_SUCCEEDED"` and `task.error_code == "ERR_NONE"` — a
   success carrying a non-zero code is a contradiction, not a pass;
3. `skills/verify.jsonl` contains a parseable measurement. An absent measurement is a
   failure, because "not measured" is not "measured good";
4. if `skills/place.jsonl` also carries a measurement, `|place - verify|` must be
   within `--max-delta-mm` (default 1.0 mm). A larger gap means one of the two is stale
   or wrong, and accepting either would launder a real error;
5. `task.final_position_error_m` is informational: dual-object tasks do not report it,
   so absence is a warning, never a failure.

The tolerance itself is not re-applied here — `VerifyObject` already applied it when it
produced `OUTCOME_VERIFIED` / `OUTCOME_MISMATCH`. What this gate adds is that the
number the run reports agrees with the number the skill server logged, and that the
skill server's number exists at all.

A run that fails any of these is a failure even if every skill returned success
(`docs/EVALUATION_METRICS.md:28-30`).

## 5. Running one task

### 5.1 Prerequisites

Source ROS and the workspace, then use the same `ROS_DOMAIN_ID`, `RMW_IMPLEMENTATION`
and `GZ_PARTITION` as the running stack. `scripts/demo_session.sh:21-22` is the
reference session (`rmw_cyclonedds_cpp`, domain 45, partition `pp-demo`); clients
started in another terminal without those exports will not see the action servers.

### 5.2 Clients

| Client | Path | Talks to |
| --- | --- | --- |
| `w1_client.py` | `src/flexcell/flexcell_skills/test/w1_client.py` | `/observe`, `/pick_object`, `/place_object`, `/verify_object`, `/run_pick_place`, `/run_demo` (`w1_client.py:26-33`) |
| `run_demo_cycles.py` | `scripts/run_demo_cycles.py` | `/run_demo` only (`run_demo_cycles.py:28`) |
| `cancel_integration.py` | `scripts/cancel_integration.py` | `/run_demo` (`cancel_integration.py:30`), plus `/flexcell/task_state` and `/reset_motion_quarantine` |

Examples, all verified against the client's argparse and goal mapping:

```bash
# Always source the project env first: ROS_DOMAIN_ID=45 + rmw_cyclonedds_cpp.
# Without it the client can see no action while `health` still reports OK.
source setup/104_mainline_env.sh

# continuous two-object demo
python3 src/flexcell/flexcell_skills/test/w1_client.py --action demo --scenario week1_demo_v1

# single-object task through /run_pick_place (the CLI verb is "task")
python3 src/flexcell/flexcell_skills/test/w1_client.py --action task \
  --object target_box_a --pose 0.12 -0.15 0.0175

# standalone measurement of where the object actually is
python3 src/flexcell/flexcell_skills/test/w1_client.py --action verify \
  --object target_box_a --pose 0.12 -0.15 0.0175 --tol 0.05

# cancel a live demo and prove the quarantine contract
python3 scripts/cancel_integration.py --out /tmp/cancel-report.json
```

`w1_client.py` prints a `RESULT {...}` JSON block and returns `0` when the outcome is a
success constant, `1` when it is not, `2` when the action server is unavailable, `3`
when the goal is rejected, `4` on a client timeout or an unknown terminal result
(`w1_client.py:132-134, 176-183, 193-201, 253-259`).

Task-state values published on `/flexcell/task_state` are `IDLE`, `BUSY`,
`RESIDUAL_CARRY`, `RESIDUAL_UNKNOWN` and `QUARANTINED`
(`task_fsm_server.py:289-294` and the publish calls). `RESIDUAL_CARRY` means a
cancelled task left the carry engaged; `RESIDUAL_UNKNOWN` means the cancel path
could not read it. Run reset before the next task. A quarantined arm refuses motion
until `/reset_motion_quarantine` succeeds.

## 6. `scripts/accept_run.py` — the per-run gate

The gate reads artifacts only; it never asks the robot process whether it did well
(`accept_run.py:1-14`).

```bash
python3 scripts/accept_run.py <RUN_DIR> [--json <REPORT_PATH>] [--max-delta-mm MM]
```

`RUN_DIR` is either one run directory or a window label directory that holds exactly
one `run-*` child; two or more `run-*` children is a failure rather than a choice
(`accept_run.py:22-26, 109-125`). Exit codes: `0` accepted, `1` rejected, `2` usage or
I/O error (`accept_run.py:34`).

| Flag | Meaning |
| --- | --- |
| `--json PATH` | Also write the report JSON to `PATH` (`accept_run.py:237-238, 253-260`). It does not replace the stdout line. |
| `--max-delta-mm MM` | Largest tolerated `place`/`verify` disagreement in millimetres, default `1.0`; must be finite and non-negative (`accept_run.py:225, 239-244`). |

Expected `RUN_DIR` layout — this is the layout `scripts/sim_profile.py` produces by
pointing every skill server's `log_dir` at `<run>/skills`
(`sim_profile.py:117`), and `scripts/sim_smoke.py` fills it:

```
RUN_DIR/
  result.json            # {"status": "...", "task": {...}}
  skills/
    place.jsonl          # one JSON object per place attempt, from place_server
    verify.jsonl         # one JSON object per verify attempt, from verify_server
```

`result.json` must be the **runner's** result object, not the raw action result:
`status` is the runner's aggregate verdict and `task` is `w1_client.py`'s `RESULT`
block (`sim_smoke.py:415, 523-536`; the client emits `outcome`, `error_code`,
`evidence_id`, `final_position_error_m` at `w1_client.py:203-212`).
The cycle record written by `run_demo_cycles.py` has different keys (`outcome` as an
integer, `succeeded`) and is **not** accepted by this tool — see
`docs/DEMO_GUIDE.md` §5.

What it reads (`accept_run.py:16-20`):

| Artifact | Field | Used for |
| --- | --- | --- |
| `result.json` | `status` | must equal `"PASS"` (`:176-177`) |
| `result.json` | `task.outcome` | must equal `"OUTCOME_SUCCEEDED"` (`:182-184`) |
| `result.json` | `task.error_code` | must equal `"ERR_NONE"` (`:185-187`) |
| `result.json` | `task.final_position_error_m` | metric `final_error_mm`; absence is a warning (`:191-202`) |
| `skills/verify.jsonl` | last line's `detail`, pattern `err=<num><unit>` | metric `verify_error_mm`; unparseable/missing is a failure (`:204-211`) |
| `skills/place.jsonl` | last line's `detail`, pattern `drop error <num><unit>` | metric `place_drop_mm`; optional (`:213-220`) |

Those `detail` strings are the ones the servers already write:
`measured within 0.060m of expected (err=0.0130)` (`verify_server.py:106`) and
`placed target_box_a: drop error 0.013m` (`place_server.py:478`). Only the **last**
non-empty line is read; a truncated last line fails closed instead of falling back to
an older row (`accept_run.py:84-106`).

Verdict and metrics in the report:

```json
{
  "pass": true,
  "reasons": [],
  "warnings": [],
  "metrics": {"final_error_mm": 13.0, "place_drop_mm": 12.0,
              "verify_error_mm": 12.0, "place_verify_delta_mm": 0.0},
  "run_dir": "/abs/path/to/run-..."
}
```

stdout is one line: `ACCEPT PASS <run_dir>` or `ACCEPT FAIL <run_dir> <reason> | ...`
(`accept_run.py:262-267`). All defects are collected, so a run that fails for three
reasons reports three reasons (`accept_run.py:12-14`).

What the tool does **not** check: the per-object zone booleans (they are derived from
the same VERIFY outcomes), the tolerance value itself, wall-clock, and whether the
scene was frozen across runs (that is the window analyzer's job,
`docs/PICK_PLACE_RELIABILITY.md:83-94`). Read `task.object_at_place` /
`task.object_a_at_zone` / `task.object_b_at_zone` from `result.json` when you report
them, and do not describe a tool PASS as a physics result beyond what §4.4 allows.

## 7. Boundaries

- **Simulation only.** Every measurement is a Gazebo model pose. No hardware grasp is
  claimed and none is measured by this interface.
- **No success-rate claim.** One PASS is one run. `docs/EVALUATION_METRICS.md:32-38`
  requires reporting `n`, the failure distribution and the evidence rung; it forbids
  a confidence interval on `n=1`.
- **n >= 50 remains frozen.** `docs/PICK_PLACE_RELIABILITY.md:161` and
  `docs/LOCAL_SIM_ACCEPTANCE_20261108.md:49-50, 58` are the current statements: a
  bounded functional window is not a success rate and does not unfreeze the
  qualification.
- **Tolerances are task-level.** Under the shipped config both task actions verify at
  0.06 m (`default_place_tolerance_m` and `demo_verify_tolerance_m` are both `0.06` in
  `src/flexcell/flexcell_skills/config/week1.yaml`). A pass at 0.06 m is not a
  precision claim: the observed spread on the same commanded release was
  2.70-13.95 mm (`docs/PICK_PLACE_RELIABILITY.md:52-53`).
- **A changed scene is not a frozen sample.** If `world.sdf` or the params changed,
  the run is still evidence but not a comparable sample
  (`docs/PICK_PLACE_RELIABILITY.md:83-94`).
