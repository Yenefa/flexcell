**状态：已实现并通过离线链路验证；未做新的机器人运行**
**入口：** `evolution/experience/` · **证据：** `setup/acceptance/evobot_continual_chain_20261118/`

## 1. 这一轮要解决的具体问题

前几轮的结论是"经验没有效果"：B/C 两组实验产出**逐字节相同的计划**。审计找到原因不在经验本身，
而在**投递地址**——经验讲的是落点坐标，而规划器只输出"物体→区域"，永远没有字段去放坐标。

所以本轮不新增经验条目，而是把下面这条链接通，并让它可被机器复算：

```
实测失败 → 经验条目 → 消费模块 → 实际行为变化 → 验证结果 → 使用记录
```

## 4. 本轮实测到的结果（这是重点）

同一条落点经验，同一份归档计划（`HO-90899d657e68`），投给两个消费模块：

| 投递地址 | 结果 | 机制 |
| --- | --- | --- |
| 规划侧 `spread()` | **NO_CHANGE** | 按**完全相等的落点**分组；计划构建器早已把两个落点错开 56 mm，没有可分的组 |
| 执行侧 `apply_respread()` | **CHANGED** | 按**距离聚类**，找到这一对，把间距从 56 mm 拉到 90 mm |

也就是说：**"经验没有效果"对某个地址成立，对另一个地址不成立**——同一仓库、同一条经验、同一份输入。

执行侧在原实现里还有一个真实缺陷，本轮一并修掉并写明边界：
`apply_respread` 只会沿 +x 展开，在这份计划上把第二个落点推到距 box_b 46 mm（< 50 mm 契约），
于是重试第三次被拒为"declared destination occupied"。修改为**按余量选轴**，并且两轴都不满足契约时**拒绝**而不是发出一个必然被拒的计划；
不传 avoid 时行为与旧实现**逐字节相同**，11/11 `benchmark/tests/test_recovery_driver.py` 仍通过。

## 4.15 上一轮那个 2.4% 是**分母用错了单位**

上一轮我报的命中率是 **2.4%**。**那个数是错的**，而错法很具体：

| 分子 | 分母 |
| --- | --- |
| `fixed` 按**任务实例**计数 | `untouched` 按**计划文件**计数 |

**同一个任务出现在多个批次里**，所以计划文件的分母大约是实例分母的 **2.7 倍**。
**一个按实例算、一个按文件算，除出来的比例就小了两倍多。**

| 口径 | 分母 | 命中率 |
| --- | --- | --- |
| 混用（上轮报的） | 7 / (7+287) | **2.4%** ❌ |
| 按**实例** | 7 / 109 | **6.4%** ✓ |
| 按**计划文件** | 7 / 294 | 2.4%（这是**文件**命中率，不是实例命中率） |

**两个数都有用，但它们不能互换，更不能相除。**
审计现在**两个分母都报**，命中率**只用同一单位的那个**（`instance_hit_rate = 6.4%`）。

**这就是"只看一个数就会自我说服"的又一例**：上一轮修的是"只记赢的"造成的偏差，
本轮发现**剩下的那个数本身也是两个单位拼出来的**。修完偏差之后仍然要对**单位**再查一遍。

## 4.16 只记赢的那几次，就是账本自己警告过的错误**反过来**

账本的 docstring 记着一条早期教训：

> "一条经验对每个任务都被检索，却一个计划也没改。"

上一轮修好了"哪次任务"，但**只记了改动的 7 次**。于是产生它的**镜像**：

| | 记录到 | 命中率看起来 |
| --- | --- | --- |
| 只记赢的 | 7 次（全 IMPROVED） | **100%** |
| 全部记录 | **294** 次（7 IMPROVED + 287 UNCHANGED） | **2.4%** |

**一个只记赢的账本，会把 2.4% 的效果报成 100%。** 这和"检索了但什么也没改"是**同一个偏差的两端**，
只是方向相反——而两端都会让人以为方法有效。

现在**每一次应用都记**，四类都记：

| 结果 | 含义 |
| --- | --- |
| `IMPROVED` | 改了，而且改对了 |
| `UNCHANGED` | **提供了、执行了、正确地什么也没做** |
| `WORSE` | 改坏了 |
| `UNKNOWN` | 技能**拒绝执行**——不算结果，但必须可见 |

**拒绝执行记 `UNKNOWN` 而不是 `UNCHANGED`**：把拒绝记成"无变化"，等于给它记了一个它没产生的结果。

顺带修掉一个把偏差写进测试的地方：一条断言写的是 `applied == total_instances_fixed`，
**那是"只记赢的"这个缺陷本身**；它会把缺陷锁死。现在是 `applied > fixed` 且 `helpful == fixed`。

还修掉一个假设：任务 ID 不只有 `HO-`（密封实例），开发集是 `T01-train-seed1000` 这种。
只判断 `HO-` 会把**整个开发集从计数里排除**——一个"哪次任务"的检查可以因此通过，
同时一半归档对它不可见。

## 4.17 账本说不出「**哪次任务**」

目标第五步写得很具体：

> 记录后续使用效果。**哪次任务**检索了它、改变了什么行动、结果怎样。

而账本里**每一条**的 `run_id` 都是 `"chain-demo"`。
**「哪次任务」的答案是演示标签，不是任务。**

| | 之前 | 现在 |
| --- | --- | --- |
| 账本 APPLIED 行 | 2（同一个标签） | 7（**7 个不同任务 ID**） |
| 记录里出现真实任务 ID | **0** | **7** |

原因很具体：复用审计是**整个包里唯一一处把技能应用到"不是它出生的任务"上**的地方，
而它把结果**写进报告文件，别处一字没有**。
**一份省略了使用过程的使用记录，会让"有真实复用证据的条目"和"从没试过的条目"长得一模一样。**

现在审计可以 `record=True`，**每个任务实例各写三行**：

| 事件 | 回答什么 |
| --- | --- |
| `RETRIEVED` | 它有没有被**提供**给这个任务 |
| `APPLIED` | 消费者的行为**有没有变** |
| `OUTCOME` | 随后那次**结果如何** |

三行而不是一行，因为别处账本一直是分开记的：
**一行合并会让"提供了但没用"和"用了而且有用"看起来一样。**
（`record=False` 时一个字节都不写，测量仍可当纯报告用；打开记录后数字完全不变——记录不是测量的一部分。）

## 4.18 过时是**双向的**，而只有一边是安全的

上一轮的 `stale_scope` 算的是 `added = measured - recorded`，**差集为空就报"没过时"**。
于是**一个声称了没人测量过的任务族的记录，通过了复核**。

而**检索照着这个声称行动**——**一个过量声明就变成了一次没有证据支撑的应用。**

| 方向 | 后果 | 严重性 |
| --- | --- | --- |
| 记录**窄于**测量 | 经验被**扣留**在一个它明明修得好的族之外 | 少一次复用 |
| 记录**宽于**测量 | 经验被**发给**一个没人测量过的族 | **一次错误动作** |

**两个方向可以同时成立**——一条记录可能在一个族上少声明、在另一个族上多声明。
用 `if/elif` 只会报它先检查的那个，**修完一半，另一半留着**。所以现在报 `both_directions`。

**修订必须能收窄。** 只能加宽的修订会让过量声明永远留着。

### 第二个缺陷：`apply()` 只执行 RETIRE

`apply()` 原来循环的是 `{"RETIRE"}`。**`review()` 可以返回 REVISE，而 `apply()` 会静默跳过它**——
**一个复核说"这条记录过时了"，动作那一半什么也没做。**
**能报出来却做不到的转换，只是一份报告。**

## 4.19 第三个转换 REVISE：**记录比测量窄了**

`lifecycle.py` 的 docstring 写着**三个转换**：RETIRE、REVISE、KEEP。**只有两个实现了。**

而 REVISE 恰恰对应**真实会发生的那种情况**：

| 情形 | 该做什么 |
| --- | --- |
| 应用过、有运行变差 | **RETIRE**（已实现） |
| 没害处，**但记录比测量窄** | **REVISE**（原来没有） |
| 都没问题 | KEEP |

`measured_families` 是**激活那一刻的快照**。之后重新测量可能超出它——
于是**活着的条目比它自己的证据还要窄**，检索会把这个经验**扣留在一个它明明修得好的任务族之外**。
**测量是对的，记录过时了。**

### 一条修订**只能改测量范围**

`revise()` 只写 `measured_families`。教训正文、适用条件、建议动作——**一个字不动**。
**一条能改写教训的"修订"，就是套着版本号的第二次未经审核的启用。**

它同时保证：

- 旧版本**留在磁盘上**（追加式）
- 链**校验通过**
- 父链接成立，状态仍 **ACTIVE**（DGM 的版本谱系）
- **会收敛**：第二遍 review 不再报 REVISE（否则那是循环，不是修复）

### 三个刻意的判断

- **有害优先于过时**：弄坏过运行的条目不管范围说什么都 RETIRE——**范围更宽只会让害处更大**。
- **测不到的消费者不算过时**：harness 消费者没有可调用绑定，仪器说"看不见它"。
  那是**仪器的盲区，不是记录的过时**；凭一个盲区去改记录，等于凭零改证据。
- **REVISED 是转换，不是结果**：把它记成"有帮助的使用"等于为一次记账变动给条目记功。

## 4.20 规划器不是「不可测」，是**只有一件事可测**

`consumers.CONSUMERS` 把规划器标为 `measurable_offline=False`，理由是"计划好不好要模型调用"。
**那是对的，但"计划好不好不可测"不等于"关于规划器什么都查不了"。**

规划器的 **SYSTEM PROMPT 自己写着**：

> If the instruction fixes an order, follow it exactly.

而 `validate_plan` **只查名字认不认识**——这句话从来没有被验证过。
归档里有 **1 个真实的重排计划**，它是在**整轮运行跑完之后**才被发现的——
**一件在执行前就能知道的事，用了最贵的方式才知道。**

现在 `validate_plan` 增加一条顺序检查（`check_plan_order`）：

| 情形 | 结果 |
| --- | --- |
| 指令说蓝块先，计划先红块 | **拒绝**，并指出哪个对象被要求先动 |
| 计划顺序正确 | 通过 |
| **指令没有规定顺序** | **完全不动**（不许凭空造要求） |
| 要求的对象根本没被移动 | 不管——**那是另一种毛病**，混淆会报出一个没找到的错 |

它**仍然不是正确性判定**：把物体放错区不会触发它，那是评分器的事。

### 一个真实的陷阱：真正的违规**跨了运行**

同一运行内的 16 份计划，**顺序全对**。唯一那次重排是
**拿 HO-128c6a 的计划去跑 HO-0dcde4d 的任务**——所以只有**用宿主任务的指令**去查，
才能看见它。**只扫同运行配对的探测器会报 0 违规，于是这条检查看起来从没被检验过。**

所以 `plan_order` 操作符**同时**报两个数：

- 同运行 16 份：**0 违规、0 误拒、16 份原样通过**
- 归档里唯一那次跨任务重排：**caught = True**

**这是规划器第一个可离线测量的效果**（不是投递，是效果）。但它**不宣称计划变好了**——
那仍然需要模型调用。

## 4.21 「量到了」和「送得到」之间有第三个断点

上一轮测出：这条落点间距经验在 **T12（3 个）和 T03（1 个）**实例上有效——**4 次胜利**。
而检索门按 `task_family` **精确匹配**。**这 4 次一次也送不出去。**

| 模块 | 内部一致吗 | 结果 |
| --- | --- | --- |
| `reuse.py` | 一致 | 测出 7 次修复，其中 4 次在别的族 |
| `retrieve.py` | 一致 | 只把经验发给"学它的那个族" |
| 合起来 | **互相矛盾** | **测量存在，投递通道用不上它** |

**一个投递通道用不上的测量，只是文档里的一个数字。**

### 底下还有第二个缺陷：`task_family` 是**默认值**，不是推导出来的

生成器里 `task_family="T13-conditional-two-boxes"` 是**硬编码默认参数**。
于是**从 T05 批次学到的 harness 教训，声明自己是 T13 落点间距教训**。
而检索**按这个标签行动**，所以该条目**被发给错的任务族，同时对对的任务族不可见**——
**一个标签，两个方向同时错。**

### 修法

1. **`task_family` 由证据推导**，两级来源：批次名（`evobot_t05_batch_...` → T05）；
   批次名不含模板时，读运行自己的 `template_id`。**推导不出就 UNKNOWN 并拒绝生成**——
   默认一个族正是产生错标签的做法，而错标签会更糟，因为检索**照着它行动**。
2. **`measured_families`** 记在激活后的版本上：**量到过**的族，与**学到的**族分开。
   检索门用两者并集。
3. **词汇统一**：`reuse` 报 `T13_geometric_conditional`，条目现在也说同一套名字。
   同一个东西两套名字，正是"测量送不出去"的来源。

修完后：**E2 被 T13、T12、T03 检索到，T14 仍被扣留**（没量过就不发）。
在 T12 与 T03 的**18 个低于契约的计划上，18/18 修好**。

## 4.22 回归门的范围是**整个检出的 70 项**，不是固定的 2 项

回归门原来按消费者钉了 **2 个** verifier——检出一共有 **70 个**。
于是"没有把原来能用的东西弄坏"这句话，实际只覆盖了 **2 项检查**。
一条经验要是弄坏了另外 68 项里的任何一项，门会说 **KEEP**。

**这是"手工划定检查范围"的典型后果：检查只覆盖了有人想到的那一部分。**

扩大范围立刻暴露第二个缺陷：**门跑遍了所有 verifier，包括装着门的那个链式 verifier**。
于是门在跑自己 → 唯一被报成"新失败"的就是包含它自己的那一项——
**一个由递归造成的 REVERT，不是回归。**

修法两条：

| 问题 | 修法 |
| --- | --- |
| 范围 2/70 | `all_verifiers()` = 全部；钉住的子集只作快速子集保留 |
| 门跑自己 | 显式 `SELF_VERIFIERS` 排除，并在 `why` 里**具名报出**被排除了什么 |

**排除是具名的，不是按通配符。** 通配符会悄悄长成"谁想跳过什么就跳过什么"。

### 基线是**测出来的**，不是估计的

70 项里有 **18 项**在 PR base 提交 `39016694` 上**同样失败**——这一条是**实测的**，
不是假设的。它们被记进 `known_failures.json`，每一条都带：

- `measured_on`：在哪个提交上测的
- `classification`：`PRE_EXISTING_ON_PR_BASE` / `STALE_RECORD` / `STATE_DEPENDENT`
- `why_not_a_live_defect`：**为什么不能归因到任何一条经验**
- `what_would_fix_it`：修它需要人工批准（它是已提交的证据）

命中 **52 项通过、18 项基线内失败、0 项新失败**。

**门要的是"没有新的失败"，不是"全绿"。** 要求全绿的门会被关掉——这个仓库里**已经关过一次**了。

顺带发现：`evobot_ladder_generated` 只在生成文档过期时失败，文档一刷新就通过。
它的结果取决于 pytest 有没有刚重新生成那个文件，**不取决于任何经验**——记为 `STATE_DEPENDENT`。
而一个"基线内但现在通过了"的条目会被专门报出来（`recovered`），否则基线会悄悄长成永久借口。

## 4.24 「order 子句失败」是**两件不同的事**

归档里有 3 行名字叫 `order` 的失败。**只有 1 行是真正的顺序错误。**

| 运行 | required | observed | 实际是什么 |
| --- | --- | --- | --- |
| `run_foreign_plan` | [b, a] | [a, b] | **REORDERED**——每一步都发生了，顺序错了 |
| `HO-2efba46248da` | [a, b] | [a] | **INCOMPLETE**——第二步**根本没发生** |
| `HO-d3ab212142de` | [b, a] | [b] | **INCOMPLETE**——同上 |

**子句名字一样，只有证据能分开它们。** 一个按 "order" 关键词分类的扫描器无法区分，
于是 3 行都会被记成"规划顺序经验"——**而其中 2 行的真因在别处**（第二步没执行），
那样教给规划器的是**修一个从来没坏过的东西**。

现在分类器读 `clauses[].evidence` 的 `required` / `observed`：

| observed 与 required 的关系 | 判定 |
| --- | --- |
| observed 是 required 的**前缀**（且更短） | `incomplete_execution`——**不是顺序经验** |
| observed 是 required 的**排列**（同集合不同序） | `order_clause_violated`——**是** |
| 其他 | `order_unclassified`——**不硬凑成经验** |

分类修正后，真正重排只剩 **1 次**，`MIN_OCCURRENCES` 正确地**拒绝**把它变成经验——
单次观测在本仓库被判为误归因风险，不是教训。

## 4.25 路由之外还有一件事：**它到底送到了没有？**

`consumers.py` 回答的是"哪个模块**有能力**执行这条经验"。它没回答"这条经验**到达**那个模块了吗"。
**这两件事之间的空隙是无声的**：

| 事实 | 后果 |
| --- | --- |
| 规划器的 prompt 渲染器读 `item["lesson"]` | v2 条目带的是 `suggested_action` |
| 两者之间没有适配器 | 教训**渲染成空条目**，计划不变 |
| ledger 记下 `NO_CHANGE` | 读起来和"这条经验没有效果"**一模一样** |

这正是目标里 `route_lessons.py` 记的那类失败——**一条真教训送进了一个承载不了它的通道**。
上一轮修的是**地址**（routing），这一轮修的是**信封**（delivery）。

`delivery.py` 为每个消费者把条目渲染成它真正读取的形状，并分三种判定：

| 判定 | 含义 | 是否可离线判定 |
| --- | --- | --- |
| **DELIVERED** | 条目内容到达了消费者的输入 | **是**（确定性） |
| **DROPPED** | 消费者会收到空的东西——这是**缺陷** | **是**（确定性） |
| **UNSUPPORTED** | 本包没有这个消费者的投递路径 | **是** |

**投递可测 ≠ 效果可测。** 规划器的 prompt 投递是确定性可测的（文本是否进了 prompt），
但计划是否变好需要模型调用，所以 `effect.probe` 对规划器仍报 **UNMEASURED**——
只是现在它能报出"投递 DELIVERED，但效果未测"，而不是"整个消费者不可测"。

把这两件事混为一谈，就会把"注入了教训、计划没变"记成关于**教训**的零结果，
而它其实是关于**信封**的。

## 4.28 复用是**在没建过它的任务上**测的（Voyager 那一环）

"它在自己出生的那个输入上有效"是最弱的结论，也是最容易被演示自然产出的结论。
**目标说的复用是：在一个任务上攒下的经验，用在后来的任务上。**

`reuse.py` 把编译好的技能资产跑遍**整个归档**（含它从没见过的任务），按任务族报四个数：

| 任务族 | 新修好的实例 | 未触碰的计划 | 弄坏 | 拒绝 |
| --- | --- | --- | --- | --- |
| **T12_triple_revisit** | **3** | 96 | 0 | 0 |
| **T13_geometric_conditional**（源族） | 3 | 101 | 0 | 0 |
| **T03_ordered** | **1** | 1 | 0 | 0 |
| T01 / T04 / T05 / T06 / T14 | 0 | 8 / 4 / 0 / 4 / 35 | 0 | 0 |

**这条经验是从 T13 的失败上学的，却修好了 T12 与 T03 的 4 个实例。** 共 7 个不同实例，**弄坏 0 个**。

两个刻意的设计：

- **按任务实例去重，不按计划文件计数**。同一个实例出现在多个批次里，按文件数会把复用结果虚增四倍。
- **"未触碰"是及格项，不是落空项**。一个资产去动一个**本来就合格**的计划是缺陷（2026-11-18 的旋转 bug 就是这么被发现的），
  只数"修好"的复用审计会奖励乱动的资产。

**报告自己写明它不支持哪个结论**：归档里所有实例都是 held-out，所以这是**跨任务族复用**，
**不是跨 split 迁移**。把两者混为一谈，就会在什么都没证明的情况下说出"它能泛化"。

## 4.30 技能参数是**选出来的**，不是手填的（GEPA 那一环）

本包里每个参数原先都是手定的：`spread_step = 0.090` 因为"间隙 0.050 加漂移余量"，
`cluster_m = 0.120` 因为"大于规划器已经给的 56 mm"。理由都成立，**但没有一个跟别的候选比过**。
一个没人比过的参数，是穿着数字外衣的猜测。而反馈已经归档，比较是免费的。

`candidate_search.py` 在 6 个候选上跑归档：

| 候选 | 可采纳 | 修好 | 破坏间隙 | 平均位移 |
| --- | --- | --- | --- | --- |
| **respread/step=0.090（采纳）** | ✅ | 33/33 | 0 | **0.0475** |
| respread/step=0.090/cm=0.060 | ✅ | 33/33 | 0 | 0.0475 |
| respread/step=0.095 | ✅ | 33/33 | 0 | 0.0497 |
| respread/step=0.100 | ✅ | 33/33 | 0 | 0.0520 |
| respread/step=0.110 | ✅ | 33/33 | 0 | 0.0565 |
| minimal_move/step=0.090 | ❌ | 33/33 | **28** | 0.0816 |

**可行性是硬过滤，成本只在可行解之间比。** 不是加权求和——加权会让一个便宜候选
"买通"一条被违反的契约。

最关键的是最后一行：`minimal_move` 就是最直觉的省事答案（保持配对中点、沿配对自身轴撑开），
在它被设计的二阶段例子上位移只有 **17 mm**（现方案 53 mm）。**它仍然被否，因为把一个落点放到
离 box_b 只有 46.1 mm 的地方——正是 2026-11-18 修掉的那个缺陷。** 只看成本会把它选上。

而它在全归档上的平均位移其实**更差**（81.6 mm vs 47.5 mm），因为三阶段计划里它只撑开第一对。
两个数字都报，谁也不许代替谁。

**无可采纳候选时返回"没选中"而不是回退到现方案**——否则"现方案是唯一能用的"和
"搜索坏了"从外面看一模一样。

## 4.32 误用检查抓到的一个真实缺陷（不是确认设计，是找到了 bug）

上一轮加误用检查时，它只用来**确认**已有失效条件是安全的。**这一轮它抓到了一个真实缺陷。**

`apply_respread` 会把 `cluster_m` 范围内的**每一个组**都重新摊开，包括那些**已经达标**的组。
而轴是按余量择优选的，所以这些组不是被原样重写，而是被**旋转**：

| 事实 | 值 |
| --- | --- |
| 归档中受影响的计划 | **127** |
| 其中**本就满足契约、完全不需要改动**的 | **94** |
| 典型例子 | `T03-train-seed1000` 沿 x 恰好 90 mm，被转到 y 轴，两个落点各移 **64 mm** |
| 修复后 | 触及 **33**，**needless = 0**，真实修复（56 mm → 90 mm）不变 |

**"恢复动作把规划器刻意选择的落点挪开 64 mm"，这不是恢复。**

修法：组内当前最小间距已 ≥ `spread_step` 时**直接跳过**。并新增失效条件与探针
`spacing.already_satisfied`——**如果它哪天报 APPLIED，说明这个回归又回来了。**

这是"不适用场景下是否会误用"这条要求第一次产生真实收益：它不只是问"我们声明做不到的场景安全吗"，
还问"这个动作会不会在它不需要的地方也动手"。

## 4.35 第一个开发集条目：读不到的证据 = 不存在

上一轮的结论是"没有开发集 T13，所以只能从 held-out 学"。**那个结论漏了一半。**

漏的是什么：`scan()` 只读 `task*.out`。而**栈压根没起来的运行不会产生 task.out**——它在扫描器眼里
不存在。归档里有 5 次这样的运行，正是 DDS 参与者耗尽那条教训。

**这条教训为什么两轮没被认出来**：它当时被归因成"Gazebo 不稳定"。证据通道里根本没有它，
所以无论怎么扫都扫不到，只能继续在运动学里找原因。

修法：`scan()` 增加第二个通道，读 `summary.txt` 里 `layer == HARNESS` 的行，并**进一步读该次运行的
`stack.log` 取真正原因**——summary 只写"stack unavailable"，那不是教训。

| 事实 | 值 |
| --- | --- |
| 归档 HARNESS 层失败 | **5** 次（t05_batch 3 次 + t05_n6 2 次） |
| 证据 split | **development**（t05 跑的是 `benchmark/tasks/train` 的 s1000–s1005） |
| 归档前/后对比 | harness 失败 **2/7 → 0/7**（n6 → n6_clean） |
| 活体契约 | 配置的参与者池 **120** ≥ 启动节点数 **6** |

所以现在**开发集能产出条目**，回退 held-out 不再必要。这是本轮的结构性改进：
链路第一次有了一条**从开发集学到的、且在开发集上验证过**的经验。

### harness 消费者从"不可测"变成"可测"

`consumers.CONSUMERS["harness"]["measurable_offline"]` 原为 `False`，理由是"config 层改动无法离线测量"。
**那句话是探针在把自己的局限说成消费者的属性。** 配置改动可以测：
1. 对着它来自的那对归档批次比前后（harness 失败 2 → 0）；
2. 对活体树查"池还大于启动节点数吗"——过去的修复不证明今天的树，后来一次编辑就能把池降回去。

## 4.4 一个必须写在最前面的限制：部分证据来自 held-out

**本链路每一条经验的证据都来自 `HO-90899d657e68`，而它在 `benchmark/held_out/unseen_public/` 里。**

事实链：

| 事实 | 证据 |
| --- | --- |
| T12/T13 只存在于 held-out | `benchmark/tasks/train` 与 `.../val` 只有 T01–T06，**零个 T13** |
| 该实例在当前封存集内 | `benchmark/held_out/unseen_public/HO-90899d657e68.json` |
| 因此没有开发集 T13 可学 | 4 条 `occupied_destination` 失败全部来自封存实例 |

**这意味着**：那两条 spacing 经验证明的是**机制可用**（条目→模块→可测行为→门→停用），
**不是**"Agent 能泛化"。在它要接受测量的那个集合上学习，然后声称在该集合上有效，是循环论证。

**但 harness 那条是例外**（见上一节）：t05 用 train 种子，证据属开发集。
所以本批次里现在**两种 split 各有一条 ACTIVE**，verifier 断言这个分布。

处置方式不是删掉结果，而是**给每条条目打上 split 标记**，并让生成器默认拒绝 held-out 证据：

- 生成器有**两条独立规则**：批次的 `evidence_index` 等级写着 "Generalization Tested"；或该次运行引用了当前封存集中的实例。第二条不依赖任何人正确标注过批次，因而能在标注漂移时仍然生效。
- 默认走开发集。本轮之前这里的产出是**零条条目**；补上 `summary.txt` 通道后是**一条**（harness）。报告同时给出 `held_out_would_exclude`，否则 held-out 运行看起来像"没有东西可排除"。
- 回退到 held-out 必须显式传参，产出条目带 `evidence.evidence_split == "held_out"`，verifier 断言它经过启用后仍然在。

## 4.5 条目从哪来：自动生成，不自审（master goal 第 1、2 步）

上一轮所有条目都是脚本里手写的。**只有人手输入经验的管道不是持续演进，是带校验的表单。**

`postmortem.py` 扫归档运行产物，按**可观测签名**聚类，满足门槛才产出 CANDIDATE 条目：

| 规则 | 理由 |
| --- | --- |
| 至少 **2 次**出现 | 本仓库曾把单次运行的观察当教训发表，后来发现是错误归因 |
| evidence 只取**解析出来的字段** | 散文是"关于测量的主张"，不是测量 |
| 消费者必须**已声明且入口存在** | 否则报 UNROUTED——"这个栈没地方放这条知识"是真实发现，不该用猜测掩盖 |
| effect_spec 必须**可执行** | 否则报 NOT_READY，不产出一条"效果只能被断言"的条目 |
| 失效条件与探针**必须一一对应** | 否则报 NOT_READY，避免下游必然 UNPROBED |
| 永不写 ACCEPT | 生成者自审会让审阅门、回归门、误用门**同时**变成摆设 |

**在真实归档上的结果**（两次运行，因为 split 不同）：

| 运行方式 | 扫描 | 结果 |
| --- | --- | --- |
| **默认（开发集）** | 36 | `harness_dds_exhaustion` 5 次 → **生成条目**，标记 `evidence_split: dev` |
| 显式 `split="held_out"` | 45 | `occupied_destination` 5 次 → **生成条目**，标记 `evidence_split: held_out` |

开发集那条来自 `summary.txt` 通道（HARNESS 层，没有 task.out）。**没有这个通道，开发集就是空的**——
所以在补上它之前，"没有开发集 T13"这个结论看起来成立，其实只是扫描器看不见。

开发集口径下 **31/31 的失败在本栈里无处安放**——`unconfirmed_native` 对应的
"从实测状态恢复"逻辑在 `recovery_driver.py` 的世界漂移分支里，不是可被 fixture 调用的函数。
这是关于这个机器人栈的发现，不是脚本的缺口。
把它硬塞进一个 `respread_apply` 的 effect_spec 里，测的就是另一个函数，
那正是"经验送给没能力执行它的模块"的同一类错误。

## 5. 检索门（四道，每道都对应一次真实事故）

1. **哈希链完好** —— 链断即拒绝整库（不"尽量学一点"）
2. **独立 ACCEPT** —— 只有 provenance 不算数：曾有两条通过 provenance 的记录在审核后被判为假，
   且它们在审核**之前**就能被检索到，并影响了计划
3. **能力匹配** —— 消费模块必须声明该 action_kind
4. **状态 ACTIVE** —— CANDIDATE / RETIRED / REJECTED 一律不进计划

## 5.5 回归门：决定"保留还是回退"（DGM 式）

启用不是"审核通过就上线"。`regression.check()` 按条目所属消费模块跑**固定的一组**验收验证器，
与 `known_failures.json` 比对：

| 结果 | 含义 | 后果 |
| --- | --- | --- |
| **KEEP** | 没有新增失败 | 允许启用 |
| **REVERT** | 出现**新增**失败 | 拒绝启用，候选留在库里 |
| **UNKNOWN** | 门跑不起来（无验证器 / 基线不可读） | **同样拒绝**——"检查不了"不等于"没问题" |

这条"UNKNOWN 不是通过"的规则来自本仓库的真实教训：`gate_differential.py` 记录过一次，
"缺少基线"曾被当成放行。启用记录里会写下 `regression.verdict` 与实际跑过的验证器名，
所以"过了回归"是可复算的陈述，不是形容词。

## 5.55 误用检查：不适用场景下会不会被打出去（master goal 第 4 步）

回归门问的是"旧任务还过不过"，它**问不了**"这条经验会不会在它自己声明做不到的场景里被打出去"。
所以 `misuse.py` 把 `known_invalid_when` 里的每一条**变成一个真实输入**，真的调用消费模块：

| 结果 | 含义 | 是否放行 |
| --- | --- | --- |
| **REFUSED** | 消费模块抛错，拒绝发出不可执行的结果 | 放行 |
| **INERT** | 消费模块原样返回，什么也没改 | 放行 |
| **APPLIED** | 在被声明不适用的场景里真的改了结果 | **MISUSABLE，拒绝启用** |
| **UNPROBED** | 声明了失效条件但没有任何可执行探针 | **拒绝启用** |

**UNPROBED 不放行**是本轮的关键判断：一条"写了免责声明但没人验过"的经验，
和一条"没人验过的门"是同一个东西。schema 还拒绝**部分覆盖**——声明三条只探测一条，
会让读者以为三条都查过了。

实测三条声明全部成立：单阶段落点 → INERT（原样返回）；三个物体进 60 mm 箱 → REFUSED；
窄箱（30 mm）→ REFUSED。执行侧三条同样成立，其中"走廊被占"→ REFUSED（两轴都不满足间隙契约）。

## 5.56 生命周期：按实际结果停用（master goal 第 5 步）

`ledger.py` 能算出 `used_harmful`，但在上一轮它**算完就丢掉了**——一条把运行变差的经验
会继续 ACTIVE、继续被检索。那不是闭环，是报告。

`lifecycle.py` 把它接上：

| 判定 | 条件 | 动作 |
| --- | --- | --- |
| **KEEP** | 无有害结果（含从未使用） | 不动 |
| **RETIRE** | 被应用过，且至少一次结果是 WORSE | 追加一个 RETIRED 后继版本 + 记 RETIRED 事件 |

**从未使用不等于有害**，所以不会因为"没人用过"就退休——沉默不是伤害的证据。

**一个必须讲清的坑**：`entry_id` 是对 body 取的摘要，而 body 含 `version.status`，
所以每次状态转换都会得到**新 id**；而 store 是追加式的，退役后**旧记录仍然写着 ACTIVE**。
第一版检索只按单条记录的 status 判断，于是退役之后**照样检索得到**——退役动作产生了零可观察变化。
修法是让检索与生命周期都按**版本线**判断：任何被后续记录声明为 parent 的 id 视为已被取代。
本轮为此加了 `superseded_ids()` 与 `latest()`，并有一条测试专门守"退役后检索必须拿不到"。

## 5.6 Voyager 式技能资产

一条经验只有在**能被下一次任务直接调用**时才算技能，否则它只是一条需要人读的笔记。
`skill_asset.compile_asset()` 把 ACTIVE 且 ACCEPT 的条目编译成资产：

```json
{"asset_id": "skill.executor_recovery.ee7177a04560",
 "callable": {"module": "runtime.recovery.recover", "function": "apply_respread",
              "kwargs": {"spread_step": 0.09, "cluster_m": 0.12}},
 "guard": ["a single stage lands in the bin", "..."],
 "source_entry": "ee7177a04560...", "code_generated": false}
```

三条硬约束：
- **参数必须有绑定**：effect_spec 里出现、但该消费模块没有对应形参的键，**拒绝编译**而不是静默丢弃
  （静默丢弃会让资产做的事与条目说的不是一回事）；
- **必须有护栏**：`known_invalid_when` 为空即拒绝——没有护栏的技能可以在已知会失败的场景被调用；
- **不生成新代码**：`code_generated: false` 写进资产。把自然语言直接变成机器人代码，
  本仓库没有证据支持，所以只把**已验证的参数改动**绑定到**已测试的函数**上。

## 6. 版本与回滚（DGM 式）

- 每个版本有 `parent_entry_id`；启用 = **追加**一个 reviewed successor，候选体保留在库中
- 重写会让哈希链把整库判为篡改，所以"激活"从不修改历史
- 失败分支保留而非删除：被拒绝的投递（E1）与成功的投递（E2）在同一份证据里并存
- `curate.curate()` 区分"重复"与"版本链"，避免把 reviewed successor 记成重复而重复计数

## 8. 复算方式

```bash
python3 setup/acceptance/evobot_continual_chain_20261118/verify.py
python3 evolution/experience/demo_continual.py
python3 -m pytest evolution/experience/test_continual_chain.py -q
```

verifier 会**重新执行**整条链并断言 **101 项检查**，不读取 SUMMARY 里的自述。其中关键几项：

- 规划侧不生效（NO_CHANGE）、执行侧生效（CHANGED）；
- 启用前后检索分别为 0 与 1；
- 启用记录里带 `regression.verdict == KEEP` 且**真的跑过验证器**；
- 启用记录里带 `misuse_check.verdict == BLOCKED`，且**每条声明的失效条件都被探测过**；
- ACTIVE 条目编译出的资产**绑定到一个真实存在的可调用函数**，且 `code_generated == false`；
- **被拒绝的投递（E1）不产出任何资产**——资产是可调用的，只有过审且过回归的条目才配变成技能；
- **六个候选被比较**，胜者修好它被评分的每一个计划、不破坏任何间隙契约、且是可行解里位移最小的；
- **被否的候选保留在板上并写明理由**；
- 生命周期复盘给出 KEEP/RETIRE 判定，**退避转换真的追加了 RETIRED 版本**、父指针正确、链仍完好；
- 退役演示跑在**副本**上，真实 store 仍只有一个 ACTIVE 条目；
- **至少一条条目来自归档自动生成**，生成器拒绝了一个 UNROUTED 签名，且**没有任何生成记录在无具名审阅者时被 ACCEPT**；
- **每条条目都声明了自己的证据 split**；开发集确实产出了条目（不是零）；没有任何被标为 `dev` 的条目引用封存实例；
- **两个不同消费者都能生效**（executor_recovery 与 harness），且 ACTIVE 条目**覆盖两种 split**；
- **命中率在同一单位里算**：109 个任务实例里 7 个生效（**6.4%**），294 个计划文件里 7 个改动（**2.4%**）——两个数都报，绝不跨单位相除；
- **账本能说出"哪次任务"**：7 个真实任务 ID，每个各带 RETRIEVED / APPLIED / OUTCOME 三行；
- **过时检查是双向的**：记录宽于测量（过量声明）同样被判过时并**收窄**，且 `apply()` 真的执行修订而不只是报告；
- **第三个转换 REVISE 真的存在**：记录比测量窄时追加一个只改测量范围的版本，旧版本保留、链仍校验、第二遍不再触发；
- **规划器有了第一个可离线测量的效果**：`validate_plan` 拒绝把指令规定的顺序倒过来的计划（16 份合规计划 0 误拒，归档唯一那次跨任务重排被抓到）；
- **量到的跨族范围真的送得出去**：检索把它发给已量到的 T12/T03，仍扣留未量过的 T14；
- **`task_family` 由证据推导**（批次名或运行 template_id），推不出就拒绝生成而不是默认；
- **"order 子句失败"被拆成两件事**：真正的重排 vs 执行被截断，且后者不被记成顺序经验；
- **每条 ACTIVE 条目都真的送到了它的消费者**（DELIVERED），参数类条目绑定到**真实存在**的可调用函数；
- 一个没有可执行文本的条目被报 **DROPPED**，一个没有投递路径的消费者被报 **UNSUPPORTED**——
  两者都不许静默算通过；
- **复用是在没建过它的任务上测的**：技能资产跑遍整个归档，修好 **7 个不同实例**、跨 **3 个任务族**（其中 2 个不是源族）、
  **弄坏 0 个**、且**未触碰任何本来合格的计划**；报告自己声明"这是跨族复用，不是跨 split 迁移"；
- 归档里 **HARNESS 层失败真的被扫到**，且其原因取自 `stack.log` 而不是"stack unavailable"这种标签。
