# PILOT 001 — Autonomous Robot Skill Development

> **研究问题**：机器人领域专用的执行反馈与独立验证机制，能否**显著提高** Coding Agent 开发机器人软件的成功率并**降低回归风险**？
> 这是**对照实验**，不是演示。若结果显示无显著差异，结论就是"无差异"——照实报告。

## 0. 与"再写一份架构文档"的区别

本试点必须产出：**两组运行记录 + 指标表 + 可复跑脚本 + 原始证据**。没有这些，视为未完成。

## 1. 实验设计（两臂）

| | **A 臂：Plain Coding Agent** | **B 臂：Robot-aware Dev Agent** |
| --- | --- | --- |
| 可见信息 | 仓库代码 + 静态检查 + 单元测试 | 同 A，**外加**：仿真执行、机器人状态、独立验证结论、证据摘要 |
| 反馈来源 | pytest 通过/失败、lint | 同上 + `sim_window`/`sim_smoke` 结果 + Verify 结论 + episode/evidence 路径 |
| 工具 | 读写文件、跑 pytest | 同 A + 跑仿真门、读证据 JSON、查指纹 |
| 禁止 | 改验证器/阈值/门禁脚本/测试断言；改世界与配置常量；跳过验证 | 同左（**同等禁止**） |
| 预算 | 同模型、同 token 上限、同 wall-clock 上限 | 同左（仿真耗时单独记账，不占用 token 预算） |

**公平性约束**：同一模型与版本、同一初始 commit、同一任务、同一预算；两臂**共享**同一套"禁止清单"；仿真耗时对 A 臂折算为"不可用但计入 wall-clock"。

## 2. 任务（3 类，各 ≥3 次重复）

| 编号 | 任务 | 类型 | 验收门 |
| --- | --- | --- | --- |
| T-A | 修改一个技能参数（如放置容差/运动档位）使指定场景通过 | 参数级 | 目标场景仿真通过 + 回归窗口不退化 |
| T-B | 新增一个组合任务（如 A→B 两段搬运），复用现有技能 | 组合级 | composite 链 `OUTCOME_SUCCEEDED` + 独立 Verify 通过 |
| T-C | 修复一个注入缺陷（预置 bug，如错误的坐标变换）使失败场景转为通过 | 修复级 | 失败场景转通过 + 无回归 |

> 任务必须**事先冻结**（写进本文件并打 tag），不得在看到结果后调整。

## 3. 流程（每臂每次运行）

1. 环境：干净 checkout + 固定 commit + 固定世界/配置。
2. Agent 收到任务说明（不含答案）。
3. 迭代：改代码 → 跑允许的工具 → 读反馈 → 再改。
4. 终止：达到门通过 或 预算耗尽。
5. 记录：每轮的工具调用、输出摘要、耗时、token、最终 diff。
6. 判定：由**独立验证器**裁决（不是 agent 自述，也不是 pytest 绿）。

## 4. 指标（预注册，事后不得增删）

| 指标 | 定义 | 采集方式 |
| --- | --- | --- |
| **First-pass rate** | 首次提交（第一轮改完）即通过门的比例 | 运行记录 |
| **Repair iterations** | 到通过为止的平均迭代轮数（未通过记满预算） | 运行记录 |
| **Task success** | 独立验证通过 / 派发任务数 | Verify 结果 |
| **Regression** | 原有窗口/技能出现新失败的数量 | 回归窗口 |
| **Cost** | token 数与 wall-clock（仿真时间单列） | 运行记录 |
| **Evidence completeness** | 必需证据项（episode/decision/verify/指纹）齐全比例 | 证据检查脚本 |
| **False success** | agent 声称完成但验证不通过（**必须为 0**） | 交叉核对 |

## 5. 防作弊与有效性保障

- **锁死**：验证器、门禁脚本、阈值、世界文件、测试断言在实验中**只读**（hash 校验）。
- **隔离**：两臂使用独立 worktree 与独立 ROS domain / Gazebo partition。
- **不自动重跑到绿**：失败即记录失败。
- **盲评**：最终判定由脚本自动给出，不由参与者人工宣布。
- **预注册**：任务、指标、预算在看到任何结果前写入本文件。

## 6. 预期产出

1. `experiments/pilot-001/<arm>/<task>/<run>/`：完整运行记录与证据。
2. 指标汇总表（含样本量与置信区间说明；样本小就明说）。
3. 一段 3 分钟视频：B 臂从需求到通过门的完整过程。
4. 结论：**支持 / 不支持 / 证据不足** 三选一，禁止含糊。

## 7. 最小可行实现（第一步，不追求完整）

先只做 **T-A（参数级）+ 1 次两臂对照**，跑通全链路（含记录与判定），再扩到 T-B/T-C。

里程碑：
- **P1.0**：脚本能自动跑完一臂一次并产出指标（不含 LLM，用"人工模拟 agent"占位）。
- **P1.1**：接入真实 LLM 作为 agent（两臂同模型）。
- **P1.2**：3 任务 × 3 次 × 2 臂，出指标表。

## 8. 风险

- 样本量小 → 只能给方向性结论，不能宣称统计显著。
- 仿真耗时长 → 需设 wall-clock 上限并记账。
- LLM 非确定性 → 固定温度/种子并重复；报告方差。
- **最容易犯的错**：把 B 臂的优势归因于"信息更多"而不是"机器人门"——需在 B 臂中区分"通用日志"与"机器人验证"两类信息，必要时加 **C 臂**（有日志无验证）。
