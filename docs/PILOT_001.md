# PILOT 001 — Autonomous Robot Skill Development（三臂对照）

> **研究问题**：机器人执行信息与独立验证反馈，各自对 Coding Agent 开发机器人软件的成功率/回归风险有什么贡献？
> 本文档是**预注册**：任务、分组、指标、预算在运行前冻结；事后不得增删。

## 1. 三个实验组（正式定义）

| 组 | Agent 可获得的执行期信息 | 要回答的问题 |
| --- | --- | --- |
| **A: Plain** | 代码、静态检查、单元测试 | 普通 Coding Agent 基线 |
| **C: Telemetry** | A + 仿真执行 + 原始日志 + 机器人状态 | 机器人执行信息本身有没有帮助？ |
| **B: Verified** | C + **独立验证器的结构化判定与失败后置条件** | 独立验证反馈有没有**额外**价值？ |

**硬约束**：三组由同一个**隐藏的独立评估器**最终判定；**A 与 C 在执行期不得看到验证结论**（B 可见）。

### 比较逻辑（预注册）

| 对比 | 含义 |
| --- | --- |
| **C − A** | 仿真/机器人观测信息的增益 |
| **B − C** | 独立验证反馈的增益（核心假设） |
| **B − A** | 完整机器人反馈机制的总体增益 |

> 注意：若 C−A 很大而 B−C≈0，则说明收益主要来自"信息"，我们的"验证"假设不成立——必须如实报告。

## 2. 公平性与预算（分开记账）

- 同模型、同版本、同初始 commit、同任务、同 prompt 模板。
- **预算三类分开记录**：token 上限、最大迭代轮数、wall-clock 上限；**仿真耗时单列**，不与"Agent 思考时间"混算。
- A 组无仿真工具；为公平，A 组的 wall-clock 上限 = 对应 C/B 组（排除仿真时间后）的 Agent 时间上限。
- 两/三组共享同一"禁止清单"：不得修改验证器、门禁、阈值、世界文件、测试断言、实验脚本。

## 3. 任务（冻结于本文件）

### T-A v2（2026-11-09 修订；P1.2 之前未产生任何数据）

**v1 缺陷（实测暴露）**：原定"`demo_verify_tolerance_m` 0.06→0.05"**不会翻转结果**——当前误差约 10 mm，两种容差都通过。冻结任务若不改变通过/失败，就无法测量。

**v2 定义**：
- 目标：把 composite 的 `clearance_m` 设到契约下限以下（如 0.02），使 `prepare_plan` 以 `ERR_INVALID_PLAN` 拒绝；把值调回合法范围（0.05–0.25）并让探针得到 `OUTCOME_SUCCEEDED`。
- 涉及文件：实验侧参数（不修改验证器/阈值/契约）；具体落点由 P1.2 run 记录冻结。
- 初始失败证据：`ERR_INVALID_PLAN` 的 probe 输出（须在 P1.2 首次运行前写入 run 目录）。
- 验收：`composite_probe` 返回 `OUTCOME_SUCCEEDED` 且无回归。

### T-A v1（已废弃，保留记录）
- **目标**：把 `demo_verify_tolerance_m` 从默认 `0.06` 改为 `0.05`，使 `recovery_once` 场景在更严容差下仍**验证通过**。
- **涉及文件**：`src/flexcell/flexcell_skills/flexcell_skills/task_fsm_server.py`（`declare_parameter` 默认值）。
- **初始失败证据**：当前默认值下场景通过，但严格容差下未验证；**P1.1 运行前必须补一次"初始失败证据"**（用容差 0.05 跑一次，记录失败/通过）并写入 run 目录。
- **验收条件**：`sim_smoke --case recovery_once` 通过 且 `final_position_error_m <= 0.05` 且回归窗口（normal A/B）不退化。

### T-B（组合级）
- **目标**：新增"两段搬运"组合（A→zone_1，B→zone_2），复用现有技能。
- **验收**：`composite_probe` 两 stage 链 `OUTCOME_SUCCEEDED` + 独立 Verify 通过 + 回归不退化。

### T-C（修复级）
- **目标**：修复一个预置缺陷（坐标系/符号错误），使注入失败场景转通过。
- **验收**：失败场景转通过 + 无回归；缺陷由实验者预置并**记录 hash**。

## 4. 每组一次的流程

1. 从冻结 commit 建独立 worktree；写入冻结 manifest。
2. Hash Guard 快照受保护文件。
3. Agent 循环：`read/write/run 工具` → 记录事件 → 预算检查。
4. 每次迭代结束：**隐藏评估器**在隔离环境中判定（写侧通道，agent 不可见）。
5. 终止：通过 / 预算耗尽 / 违规。
6. 收集证据（episode、decision、verify、fingerprint）。
7. 产出指标行。

## 5. 指标（预注册）

| 指标 | 定义 |
| --- | --- |
| First-pass rate | 第 1 轮修改后即通过验收的比例 |
| Repair iterations | 通过所需轮数；未通过记满预算 |
| Task success | 独立评估器通过 / 运行数 |
| Regression | 回归门新增失败数 |
| Cost | token、Agent 时间、**仿真时间单列**、端到端时间 |
| Evidence completeness | 必需证据项齐全比例 |
| **False success** | Agent 声称完成但评估器不通过 —— **按组记录实数**；B 组工程目标为 0，其他组出现是重要结果，不得剔除 |

## 6. P1.0 验收（本阶段）

必须交付**可运行**的：
1. `manifest` 冻结与校验；2. 三臂 Runner（工具权限隔离）；3. Hash Guard；4. Event Recorder；
5. Evidence Collector；6. 独立 Judge；7. Metrics Engine。

**五个夹具必须全过**：正常通过 / 任务失败 / Agent 虚报成功 / 受保护文件被改 / 必需证据缺失。

> P1.0 的"人工模拟 Agent"只验证**测量链路**，不产生任何"假设成立"的证据。

## 7. P1.1 / P1.2
