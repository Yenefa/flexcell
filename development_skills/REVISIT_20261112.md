## 二、为什么这些**都不是**有效证据

### 「接口类错误 0 次」是混淆，不是效果

```
Skill 写入之前：6 次接口错误
Skill 写入之后：9 次运行，0 次接口错误
```

看起来像有效。但**这 9 次运行用的是修好之后的驱动脚本**——错误已经被修掉了，本来就不会再犯。

**没有做「有 Skill / 无 Skill」的对照**，所以无法区分：是 preflight 拦住了，还是代码本来就对了。

**这正是用户提醒的那个陷阱：避免把其他改进误归因给 Skill。**

### 「孤儿进程 0」什么也没说明

现在机器闲置，`gz=0` 是理所当然的。真正的指标是**批次跑完后的残留**，不是**什么都没跑时的残留**。

### 「preflight 被调用」只证明接上了

接上不等于拦到东西。一个永远返回 0 的检查也会显示「被调用」。

它确实拦到过一次：它自己的 `get_field_and_field_types` 拼写错误，第一次运行就被自己报出来。
但那是**开发期自检**，不是生产拦截。

### 「验证器有调用方」不是 Skill 的功劳

那是 v0.5.0 集成修复的结果，而 `evidence-level-audit` 是在修复**之后**总结出来的。

**把已经发生的事算作 Skill 的效果，就是自我欺骗。**

---

## 三、要得到有效证据，需要什么实验

### 对照设计

```
任务：同一个需要新写 ROS 脚本的工作（例如 T09 或 T10 的执行驱动）
A 组：不给 Skill，让 Agent 直接写
B 组：先加载 Skill，再写
记录：首次运行成功率、接口类错误次数、从开始到首次成功的时间
```

### 为什么必须是这类任务

必须让 Agent **真的可能犯那个错**。在已经修好的代码上跑，永远不会产生反例，实验没有信息量。

### 最小可接受证据

| Skill                        | 可证伪的指标                   | 门槛              |
| ---------------------------- | ------------------------------ | ----------------- |
| ros2-interface-preflight     | A 组接口错误次数 / B 组        | A >= 1 且 B = 0   |
| simulation-process-lifecycle | 批次后残留进程数               | A >= 1 且 B = 0   |
| evidence-level-audit         | 「测试绿但无调用方」是否被查出 | B 组至少查出 1 个 |
| effect-verification          | 「空输出当成功」是否被拦住     | B 组至少拦住 1 次 |

**在拿到这类数据之前，四个 Skill 一律保持 PROPOSED。**

## 四、这一轮回访本身暴露的问题

**回访机制建起来了，但它现在无法自我验证。**

这不算失败——它诚实地说明了三件事：

1. Skill 库目前是**未被证伪**的，不是「已被验证」的；
2. 唯一能证伪它的方法是对照实验，而对照实验需要新任务；
3. 在此之前，任何人把 Skill 库当成绩，都是把文档当成果。

**下一轮的 Curator 应当在新任务上做上面的对照，而不是再总结一批 Skill。**
