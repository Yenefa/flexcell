# 证据等级审计

**状态：`PROPOSED`**（测试通过 ≠ 有价值；尚未有回访数据）

---

## 什么时候触发

- 要声称「某个验证器有效」
- 要声称「某批实验通过」
- 一个模块有完整单元测试，但还没确认有调用方
- 写验收报告时要引用测试数量或通过率

## 什么时候**不能**用

- 纯粹的内部重构（没有对外声称）

**本 Skill 只审查「声称」与「证据」是否对应，不审查代码质量。**

---

## 为什么需要它

本会话两次，方向都很危险：

### 事件 A —— 65 个测试全绿，而生产路径从不调用它

```
verify.py          65 测试全绿
evaluate.py v0.4.0 从不 import 它
```

**一个没人调用的验证器就是一份文档。**

更糟的是，那个验证器本身明明有 9 个门，`evaluate.py` 只用了其中一个数字（`max_z`）。
修复后立刻发现一个错误：`evaluate.py` 不传 limits，三个限值依赖门全部 fail closed
（`no lift limit supplied`），**每一次真实推都会被判失败**。

### 事件 B —— 报告声称 8/9 门通过，实际 6/9

```
报告写:  9 门中 8 门通过
修复接线后实测:  9 门中 8 门通过   <- 现在才对
修复前实测:      9 门中 6 门通过   <- 当时是错的
```

**结论对，算术错，而且错的方向是美化工作。**

## 必做步骤

```bash
# 1. 检查「被验证的东西」是否真的被调用
python3 scripts/call_path_check.py --symbol verify --expect-caller benchmark/evaluators/

# 2. 报告里每个数字都要能复算
#    见 references/claim-checklist.md
```

## 验证方法

```bash
python3 -m pytest tests/ -q
```

## 失败时如何安全退出

```
有测试无调用方  -> 停止，不要说「已验证」
数字无法复算    -> 删掉那个数字，不要估
```

## 四层证据（不得互相冒充）

| 层          | 由什么证明             | **不能**推出     |
| ----------- | ---------------------- | ---------------- |
| L1 合成验证 | 单元测试通过           | 机器人做过任何事 |
| L2 遥测集成 | 真实数据被读成合法结构 | 任务完成         |
| L3 仿真实跑 | 真实一次运行的门判定   | 任务验收通过     |
| L4 独立验收 | `passed=true`          | 泛化能力         |

**任何一份报告必须写明自己在哪一层。**

---

## 适用范围

| 覆盖         | 不覆盖             |
| ------------ | ------------------ |
| 调用方存在性 | 调用方逻辑是否正确 |
| 数字可复算性 | 实验设计是否合理   |
| 四层证据分离 | 机器人能力评价     |
