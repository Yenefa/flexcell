**错的是我的复算，不是报告。** 但根因仍然是个真缺陷：

> **一个声称"可复算"的数字，它的判据不全在已提交的工件里。**

## 三、最便宜的有效实验（下一轮照做，不需要再决策）

### 首选：`ros2-interface-preflight` 的**离线** A/B —— 0 次 Gazebo

**为什么是它**：它要防的错误是纯静态的，所以对照实验**完全不需要仿真**。
这是四个 Skill 里唯一能在不碰 Gazebo、不占 sim lane、不烧模型的前提下做真实 A/B 的。

**任务**（本来就要做，见 HANDOFF §4(2)：unseen 实例 3000–3002 一次都没跑过）
让一个 Agent 写一个新的 T08 驱动：从 `benchmark/tasks/t08_unseen/T08-push-seed3000.json`
构造一个 `PushObject.Goal`，并输出它读到的 `PushObject.Result` 字段名。

**分组**

| 组 | 给什么 |
| --- | --- |
| A（无 Skill） | 只给任务描述 + 仓库路径。**不读 `development_skills/`** |
| B（有 Skill） | 同一段任务描述 + "先读 `development_skills/ros2-interface-preflight/SKILL.md`，按它跑 `scripts/preflight.py --describe`，再写" |

**指标（两个，都可离线数）**

1. **接口类错误次数**：驱动第一次跑到"成功构造 Goal"之前，stderr 里出现
   `AttributeError|has no attribute|TypeError` 的次数。用 `revisit_r2/interface_error_scan.sh` 数。
2. **到首次成功的尝试次数**：从第一次运行到第一次打印出正确字段名列表，中间改了几次。

**可证伪门槛**：A ≥ 1 且 B = 0 → preflight 有效；A = 0 → 任务没有诱发该错误，实验无信息量，**不得记成"Skill 有效"**。

**成本**：2 次 Agent 运行 × 约 10 分钟；**0 次 Gazebo**；0 次付费模型调用；
ROS 只需 source，不需要启动任何东西（`--describe` 只 import 消息定义）。

## 六、本轮识别出的三个新候选模式（**不是**已存在的四个 Skill）

Lead 点名的两个模式，我逐条测了。结论是：**两个都是真候选，但都不是"再写一份文档"能解决的，
而且第二个的严重性比 Lead 描述的低——我实测到它的冗余缓解。**

### 候选 P1 · 「标签声称的出处，没有任何东西去核对」

**复发次数：2 次/轮，且同轮内被发现者互相独立确认。**

| 实例 | 事实 | 发现者 |
| --- | --- | --- |
| `baseline_a_v2_gated_20261111/` 标为 A′，实为 **oracle** 输出 | 72/72 字节相同，本 Curator 独立复现 | Lead → gate-auditor → 本 Curator（三次独立） |
| 三个不同模块都叫 "A′" | `baseline_a_composite.py`（**唯一真读 `expected_goal`**）、`baseline_a_prime_rules.py`、`rule_planner.py`、`rule_planner_t01_t06.py` | gate-auditor §4 |
| `evobot_p0_paired.sh` 从未成功运行（`IndentationError`），却是一份"配对执行"流程的出处 | 全仓库无 `paired.tsv` | gate-auditor §5 |

**我自己的实测（`revisit_r2/provenance_label_check.sh`）：**

```
archived instances: 72
rebuilt from experiments/baselines/build_composite_plan.py:
  byte-identical to archived 'A-prime': 72
  differing:                            0
```

**归属判定：并入 `evidence-level-audit`，不新建目录。**

理由：它的目标失败是"测试绿但无调用方"，即**「一个被信任的东西其实没接上」**。
本轮这个是**「一个被信任的标签其实指错了生产者」**——同一形状：
**信任关系存在，核对关系不存在。** 拆成两个 Skill 只会让两个都半死不活。

**最便宜的检测脚本（已有雏形，`provenance_label_check.sh`，约 40 行）：**

| 步骤 | 做法 | 成本 |
| --- | --- | --- |
| 1 | 解析 `verify.py`/文档里的 "label -> producer" 声明 | 静态 |

| 4 | 额外查 AST：被称作 "oracle" 的模块是否真读 `expected_goal` | 秒级 |

**成本：0 次 Gazebo、0 次模型调用、约 40 行代码、全仓库扫描 < 30 秒。**
**这已经跑通了**（上面 72/72 就是它输出的）。**但它还没有被任何开发流程采用，所以是 NOT_MEASURED，不是 VERIFIED。**

### 候选 P2 · 「一个检查，拿同一个生产者提供的另一个数去比」

**这一条我实测后发现 Lead 的表述需要修正。**

Lead 说"六个门都靠自声明参考值"。实测**不是六个**：

| Lead 点名的值 | 谁在读 | 判定 |
| --- | --- | --- |
| `rest_height_m` | `_gate_table_support`(133) + `_gate_no_lift`(208) | **是**比较操作数 |
| `pusher_links` | `_gate_pusher_contact`(235) | **是**比较操作数 |
| `max_z_m` | verify.py 里 **0 处**；由 evaluate.py 从 observation 读 | 不同通道 |
| `bundle_sha256` | verify.py **0 处**；schema.py:279 只查 `isinstance(str)` | **未校验** |
| `max_gap_ns` | verify.py **0 处**；schema.py:133 只查范围 | **未校验** |
| `dropped_samples` | verify.py **0 处**；schema.py:131 只查范围 | **未校验** |

**9 个门里，3 个（table_support / no_lift / pusher_contact）确实拿 bundle 自带的参考值作比较。**

**但冗余缓解是实测成立的**（`revisit_r2/forge_test.sh`）：

```
F1 carry, rest honest                         passed=False  failed=['no_lift','table_support']
F2 carry + rest_height_m re-declared to apex  passed=False  failed=['table_support']
F5 pusher_links invented                      passed=False  failed=['pusher_contact']
```

- **F2**：把 carry 藏起来需要改 `rest_height_m`，但 `table_support` 是**双边**判据
  （每个采样都必须在静息高度 ±容差内），改参考值反而触发它。**冗余挡住了单点伪造。**
- **F7**：把 bundle 摘要清零**什么都不发生**。**没有门校验封印。**
  这是独立于 P2 的一个实测洞，且**不在 Lead 列的六项里**。

**归属判定：作为 review 问题并入 `evidence-level-audit`，不新建 Skill。**

一句话形式（可直接进 SKILL.md 的检查清单）：

> **对每一个门问：它拿来比较的那个数，和被检查的证据，是不是同一个不可信生产者给的？

**最便宜的检测脚本：`self_declared_reference_check.sh`（已跑通，约 30 行）。**
它用 AST + 行归属把"每个门读了哪些 bundle 字段"打出来，人只需要对每个门回答上面那一句。

### 候选 P3 · 「被引用的指标，在它被引用的那个子群上恒等于另一个量」

**这一条是在我写报告期间才落地的**（`evobot_t04_executor_mismatch_20261112/README.md`，exec-mystery lane）。
我不采信结论，直接验了它的**规则**：

```
evaluate.py:254  claimed       = bool(final_state.get('agent_claimed_success'))
evaluate.py:343  false_success = bool(claimed and not passed)
evaluate.py:344  false_failure = bool(passed and not claimed)
```

穷举 `(passed, claimed)` 真值表（`revisit_r2/degenerate_metric_check.sh`）：

| passed | claimed | false_success | false_failure |
| --- | --- | --- | --- |
| False | False | False | **False** |
| False | True | True | False |
| True | False | False | **True** |
| True | True | False | False |

**在 `claimed=False` 的两行里，`false_failure` 与 `passed` 完全相等。**

```
identity holds for every claimed=False row: True
```

所以 exec-mystery 测到的 "9/9 全部 false_failure=true" **不是经验发现，是算术必然**——
那 9 次 B 运行都没有 agent claim。**这个数在它被引用的子群上携带零信息。**

**归属判定：并入 `evidence-level-audit`，同样不新建目录。**

理由与 P1 同根：都是**「一个被信任的结论，其成立条件没有被检查」**。
P1 是标签的出处没核对，P2 是门拿同源数据对比，P3 是**指标在自己失效的子群上被引用**。

**最便宜的检测脚本：`degenerate_metric_check.sh`（已跑通，约 30 行，纯算术）。**

通用形式，可直接进 SKILL.md：

> **对一个指标 M(A, B)，检查它在"实际被报告的那个子群"上是否退化成 A 或 B。
> 如果退化，在那里引用 M 就是在用第二个名字引用 A。穷举真值表即可，成本为零。**

**成本：0 次 Gazebo、0 次模型调用、纯算术、毫秒级。**
