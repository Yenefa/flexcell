## 一、项目题目
**AgenticFlex：面向教育与柔性装配的智能体驱动机器人工作单元**

## 二、项目摘要
本项目构建一个"智能体（agent）驱动机器人"的柔性工作单元：用户用自然语言下达任务，系统经由**分层决策**
（决策层→技能层→执行层→独立验证层）把任务拆解为可安全执行的技能动作（观察、抓取、放置、验证），
在仿真与真机上均可运行，并把每一步决策、观测与结果**证据化留存**、可离线复现。相比传统硬编码脚本，
它把"机器人怎么做事"与"要做什么"解耦：agent 负责意图，工作单元负责安全、可验证地执行。

## 三、项目背景与国内外研究现状
- 背景：AI 大模型与机器人结合成为热点，但"会聊天"到"能安全干活"之间缺少可靠的运行时契约与验证。
- 现状：Isaac/ROS-MCP 等生态提供工具与开发平面；工业机械臂编程仍依赖专家脚本；教学实训缺少"可复现、可审计"的一体化平台。
- 机会：把"agent 技能调用 + 分层安全执行 + 数据闭环"做进一个可教学、可研究、可迁移的工作单元。

## 四、研究内容与技术路线
1. **决策层**：WorldState v2 + DecisionPolicy 接口；内置 FSMPolicy 参考实现，可切换 Jev/LLM/Hybrid，失败时**降级不 deadlock**。
2. **技能层**：observe / pick / place / verify 四类技能，统一失败语言；运动规划经 MoveIt 2 / MTC 走同一执行器。
3. **执行层**：ROS 2 Jazzy + ros2_control + Gazebo Harmonic（可信仿真）；同一套 launch 可切真机。
4. **验证层**：独立 Verify 技能 + 安全门（目标/可达/碰撞/预算），拒绝越界提案。
5. **数据闭环**：LeRobot 标准记录 + rosbag 对账回填（解决实时丢帧），导出前门禁校验采样间隔。
6. **迁移成本基准（TransferBench）**：按参数/对象/组合/恢复/平台五轴度量"从冻结起点到新任务"的工程成本。
7. **持续演进层（continual）**：每次失败落成一条**带消费模块与可执行效果**的经验条目，按能力路由到真正能执行它的模块，在后续任务中复用，并用回归检查决定保留还是回退（详见第七节）。

## 五、创新点
1. **技能契约 + 策略路由**：agent 只调用声明式技能；决策策略可插拔并在异常时降级，兼顾灵活与安全。
2. **证据化、可验证**：每步 decisions/episode/帧与独立验证结果留痕，支持离线策略输入回放，教学与科研可审计。
3. **可信仿真-真机一致 + 数据闭环**：可复现的 profile 与 rosbag 对账，使"仿真验证过的行为"可解释地迁移到真机。
4. **迁移成本可度量**：TransferBench 让"加一个新任务要花多少工程投入"第一次被量化。

## 六、应用前景与社会价值
- 市场：高校/职教机器人与 AI 实训平台、实验室自动化、小件柔性装配与分拣。
- 社会价值：用自然语言降低机器人使用门槛，让非专家也能安全驱动机器人；证据化让教学可复现、科研可比较。

## 七、持续演进（continual）主线

**目标**：EvoBot 面向机器人任务，持续积累**经过执行验证**的经验与技能，在后续任务中复用，并通过回归检查决定是否保留更新。基座模型冻结，演进发生在技能、参数与策略层，因此每一次改动都有 diff、有 SHA、有回归记录。

**五步机制**（每一步都有代码入口，不靠文档约定）：

| 步骤 | 做什么 | 代码入口 |
| --- | --- | --- |
| ① 抽机制 | 先解决"哪些经验值得保留" | `evolution/experience/schema.py` |
| ② 成条目 | 七字段 + 消费模块 + 可执行效果描述；**从运行日志自动生成** | `schema.make_entry` / `postmortem.py` |
| ③ 出产物 | 规划规则 / 恢复策略 / 技能参数，每项有明确调用入口 | `evolution/experience/consumers.py` |
| ④ 先验证再启用 | **候选搜索（可行性硬过滤＋成本）** → 执行效果 → 独立审核 → **回归门 KEEP** → **误用检查 BLOCKED** → 追加式启用 | `candidate_search.py` / `effect.py` / `regression.py` / `misuse.py` / `curate.py` |
| ⑤ 记使用效果 | 检索、应用、结果分开记，**有害则停用** | `ledger.py` / `lifecycle.py` |
| ⑥ 沉淀为技能 | 过审且过回归的条目**编译成可调用资产**（模块+函数+绑定参数+失效护栏） | `skill_asset.py` |

**关键设计——经验必须送给有能力执行它的模块。** 消费模块主动声明自己能执行哪类改动，条目按**能力**路由而不是按关键词猜地址。这条规则来自一次实测：同一份落点经验投给规划器后，计划**逐字节相同**；把同一经验投给执行侧重排模块，落点间距从 56 mm 变为 90 mm，且保持 81.4 mm > 50 mm 的间隙契约。**"经验没有效果"因此是一个地址问题，而不是经验问题。**

**检索四道门**：哈希链完好 → 独立审核通过 → 模块能力匹配 → 版本状态 ACTIVE。任一道不过即不进计划，空检索也会被记录（"通道为空"与"没人查过"不是一回事）。

**回归门决定保留还是回退**：启用不是"审核通过就上线"。按条目所属模块跑固定的一组验收验证器并与已知失败基线比对——**KEEP 才启用**；出现**新增**失败即 **REVERT**；门本身跑不起来则记 **UNKNOWN，同样拒绝**（"检查不了"不等于"没问题"，这条规则来自本仓库曾把"缺少基线"当成放行的真实教训）。

**误用检查决定"会不会用错地方"**：每条经验都自带"已知失效条件"，这些条件被**逐条变成真实输入并真的调用执行模块**。结果是拒绝（REFUSED）或原样不动（INERT）才算安全；真的在被声明不适用的场景里改了结果即 **MISUSABLE，拒绝启用**；声明了条件却没有任何可执行探针即 **UNPROBED，同样拒绝**——"写了免责声明但没人验过"和"没人验过的门"是同一件事。

**按实际结果停用**：检索、应用、结果三类事件分开记；若某条经验被应用过且至少一次结果变差，则**追加一个 RETIRED 版本**停用它，旧的（有害的）版本仍留在库里。从未使用不算有害，沉默不是伤害的证据。

**版本保留**：启用不是覆盖，而是**追加**一个带父指针的已审核版本，候选体与失败分支都留在库里；重写历史会被哈希链判为篡改。

**沉淀为可执行技能**：条目只有被下一次任务**直接调用**才算技能。过审且过回归的条目编译成资产，绑定到**已测试**的函数与固定参数，并携带失效护栏；参数没有绑定就拒绝编译（避免静默丢弃导致"做的与说的不一致"）；不生成新机器人代码（`code_generated: false`），因为把自然语言直接变成机器人代码在本项目中尚无证据支持。

**本轮做到什么程度（如实标注）**：
- 已实现并离线验证：条目模式、**从运行日志自动生成条目**、能力路由、效果执行器、去重/冲突整理、检索门、**回归门**、**误用检查**、**GEPA 式候选搜索**、**投递可达性检查**、**失败归因区分**（顺序错误 vs 执行截断）、**全量回归门**（69/70 项，基线经 PR base 实测）、**跨任务族复用审计**、追加式版本链、使用账本、**按实际结果停用**、**可执行技能资产**（`verify.py` **150/150** 项检查可复算）。
- **未做**：新的机器人运行；外部（非同一运行内）独立审核；跨任务族迁移（当前活跃条目只覆盖一个任务族，n=1）；技能资产的自主组合编排；回归门覆盖全部验证器（现按模块固定子集）；**退役的真实触发**（本轮没有运行变差，退役只在副本上以合成事件演示）。
- **自动生成的范围有限**：生成器能读归档并产出候选，但"签名→消费模块"的映射表仍由人维护；开发集口径下的 31 次归档失败全部落在表外，被如实报为 UNROUTED（本栈没有能执行它的可调用函数），而不是硬塞进一个测着别的函数的规格里。
- **两条经验来自 held-out，一条来自开发集**：T12/T13 任务族**只存在于 held-out 集**（训练/验证集只有 T01–T06），所以那两条 spacing 经验证明的是**机制可用**，不是"Agent 能泛化"。每条经验都带 `evidence_split` 标记，生成器默认拒绝 held-out 证据。
- **开发集条目是怎么找到的**：扫描器原先只读 `task*.out`，而**栈没起来的运行不产生 task.out**，于是 5 次 HARNESS 层失败（DDS 参与者耗尽，曾被误归因为"Gazebo 不稳定"）在扫描器眼里根本不存在。补读 `summary.txt` 并进一步读 `stack.log` 取真实原因后，开发集才第一次产出条目（t05 用训练集种子，harness 失败 2/7 → 0/7）。
- **技能参数是选出来的，不是手填的**：6 个候选在归档上按"可行性硬过滤 + 成本择优"比较，一个更省位移但破坏间隙契约的候选被否并保留在板上（只看成本会把它选上）。
- **"路由到"不等于"送到了"**：经验条目带 `suggested_action`，而规划器的 prompt 渲染器读 `item["lesson"]`——两者之间原本没有适配器，教训渲染成空条目、计划不变、账本记 `NO_CHANGE`，**读起来和"这条经验没效果"一模一样**。现在为每个消费者显式渲染并判定 DELIVERED / DROPPED / UNSUPPORTED（三者都确定性可测）；规划器的**效果**仍标 UNMEASURED，但它能说"已送达、效果未测"，而不是"这个消费者不可测"。
- **已提交的证据必须还是代码现在的样子**：验证器每轮在临时目录重跑，所以能查"代码自洽"，查不出"已提交产物已陈旧"——两者**已经走散**（32 个文件里 18 个）。根因是 `review_ref` 把**绝对输出路径**嵌进条目正文，`entry_id` 随运行目录变；那条引用还指着一个**从未写出的文件**。现在改为指向实际写出的文件的相对路径，并用 `evidence_freshness` 对比已提交产物与新运行：**数字漂移、缺文件 → 失败**，id 变动只按"证据年龄"报告（比字节会在每次无害 schema 改动上失败、一周内被关掉）。
- **不许出现"没有条目支撑的活规则"**：规划器的顺序规则一度被直接接进校验函数，**规划器开始拒绝它以前接受的计划**——一次真实的线上行为改变，而**背后没有条目**，于是没人审过、没测过误用、查不到使用记录、**也无法退役**。这正是目标第四步要禁止的事。现在规则**只在有条目投递过来时生效**，无条目时行为与改动前完全一致；规则本身仍可单独测量（**测量 ≠ 启用**）。
- **适用性门覆盖全部声明**：上一轮报「已检查适用条件」，实际只查了 E2 四个失效条件里的一个，还把一个探针 ID 拼错（`spread.single_stage` vs `respread.single_stage`）。现在逐条遍历 `invalid_probes`：能查的查、查不了的记入 `unprobed` 并**整门拒绝**——没有 live 检查的免责声明不是保障。结果是 `checked=4, unprobed=0`。
- **审核不能早于条目生成**：`entry_id` 是正文摘要、可预测，审核者能在条目写入前预生成 ACCEPT。现在审核必须同时带 `entry_chain_sha256`（条目及其前序真正写入后才确定），预生成审核被拒；如实声明攻击者若控制整条链仍可构造——那需要签名机制。
- **第 5 步在 live 边界接通**：实际应用写 RETRIEVED/APPLIED/OUTCOME 三行并带真实 run_id；**回退到默认时一行都不写**——把回退记成 APPLIED 会重新制造早先修掉的「只记成功」偏差，端到端测试固定了这三种情况。
- **live 门按真实计划检查适用条件**：目标第 4 步要求"不适用场景不得误用"；之前误用探针只跑在归档 fixture 上。现在 `resolve()` 接收真实 `plan.json`，在参数到达 `apply_respread` 前按**条目自己声明的**失效条件与阈值判断：已符合契约（90 mm）或单个落点的计划**拒绝**，低于契约（56 mm）才放行；改条目即可改行为，门本身通用。
- **最关键的一道门，账本本身防篡改**：独立审核账本原本是普通 JSONL，**手写一行假审核就能放行**（实测）。现在每条审核带 `review_sha256`/`chain_sha256`，门在消费授权前先验链——伪造行、事后改判定都被拒。同时如实声明哈希链**不能证明审核者身份、不能阻止新审核、不能发现尾部截断**；一条原本断言"删尾会被发现"的测试是在要求哈希链根本不提供的性质，已改为检测中间删除。
- **授权必须来自独立账本、并绑定确切 entry_id**：之前门读的是条目自己正文里的 `reviewed_by`——同一轮自写，链只能证明没被篡改，**不能证明有人独立签字**。仓库里确实有独立 ACCEPT（gate-auditor），但那是**同一份证据上另一条声明**（控制事实），搬过来给 E2 的可执行建议背书就是拿真审核替假主张担保。现在门读独立账本，要求 `entry_id` 相符 + ACCEPT + 审核者非自审；**无账本/别的声明/自审者三种全拒**。
- **live 调用接上了 opt-in、fail-closed 的接线**：`recovery_driver.py` 新增可选参数，`resolve()` 在参数到达 `apply_respread` 前重验四道门（链完整、ACTIVE+最新、**独立 ACCEPT**、从**条目**派生的有限数值 kwargs）。无参数时冻结基线逐字节不变；自审条目被拒（**自审不算独立复核**）；参数从条目派生而非资产缓存字段——**改资产文件不能操纵机器人**。接线已通，当前条目因只有自审仍驱动不了机器人——**这是门在尽职，不是接线失败**。
- **接通缺口经过两次修正，根因是「消费者不读条目」**：第一次归为模式不匹配（错——非规划器类别按设计拒绝，桥接无效），第二次归为没有消费者（错——漏看 shell runner）；实际上 `run_batch.sh:107` → `recovery_driver.py:146` → `apply_respread` 消费者**存在**，但它用**默认参数、不查条目**——条目将来被修订，机器人永远收不到。三次诊断一次比一次窄、一次比一次准。
- **接通缺口的根因是"没有消费者"，不是"模式不匹配"**：两条 ACTIVE 条目分别是 `tooling`/`control` 类，live 检索只收 planning/state——**做模式桥接不会有任何效果**。真正的调用点是：live 脚本里 `harness` 与 `executor_recovery` 的调用次数**各为 0**——链学会了改进机器人从不读取的模块。上一轮归因为模式不匹配，**本轮修正**。
- **链正确，但没接入真实机器人路径**：两个存储、两套模式——链写 `records_v2.jsonl`（`entry_id`/`suggested_action`/`consumer`），真实路径 `baseline_c.py` 读 `records.jsonl`（`lesson`/`validated`/`provenance_verified`）。**2 个 ACTIVE 条目，0 个对真实路径可见**；顺序规则也因 `baseline_c` 的经验项没有 `_entry_id` 而永不触发。两种接线方案都有代价（v2 缺过滤器所需字段会被全部拒收；改 live 路径要动冻结基线读的文件），所以**报数字与代价，不假装闭合**。
- **第三种答案：模块存在，但归档量不出效果**：`graded_push`（23 次，最大未路由签名）有真实模块 `push_recover`（记录 2/5→4/5），但**记录的尝试是该策略自己产生的**——回放自己的输出量不出它改变了什么，这是**选择效应**而非"无效果"。报 UNMEASURED + `module_found`，三种诱人的答案（无模块/已正确/仍有错）都不给；回放 5/5 复现判决只算**回放正确性**，不算效果。
- **"UNROUTED"是"我们没写映射"，不是"没有模块能用"**：生成器把 7/9 签名判为 UNROUTED，覆盖 **92/98** 个失败。现在逐条量：`placement_clause_failed`（14 次）测出**规划器 6/6 已选对箱子**——把它当经验投给规划器**什么都不会变**，正是目标里 `route_lessons.py` 那个坑的翻版；其余 6 个如实报 **UNMEASURED**（没写探针，**未知**而非已知为否），候选消费者明确标注为**假设**。
- **第四条路由（ROS 启动经验→开发经验）现在真的送得进去，而且不冒充已验证**：注册表里 **PROPOSED = 已写、已单测、已做变异测试**，经验条目没有测试文件——写成 PROPOSED 就是往注册表塞一个没发生过的验证。所以渲染为**候选**、`effect: NOT_MEASURED`、并**点名自己缺 entrypoints/tests/mutation**；没有 `applicable_when` 的条目直接 **DROPPED**（没有触发条件的技能永远不会在对的时机被加载——这正是采纳率为 0 的失败模式）。"空路由"（路径通、没人投）与"送不进去"（有条目、到不了）现在**分开报告**。
- **"路由已声明"不等于"路由已覆盖"**：目标点名四条路由，本栈四条都声明了，但**只有一条真的在送货**（抓放恢复→执行器）。ROS 启动经验→开发经验这条**声明了，`delivery` 对它返回 UNSUPPORTED，什么都送不进去**——正是本包已为别的消费者修过两次的"routed but undeliverable"。现在逐条报告为 CARRIED / NAMED_BUT_EMPTY，**不把声明当覆盖**；ROS 启动教训实际在 `harness` 上生效，**单独报、不计入四条覆盖**，避免向上取整。
- **账本不美化命中率、也不跨单位算比例**：**109 个任务实例**里 7 个生效 = **6.4%**；**294 个计划文件**里 7 个改动 = **2.4%**。上一轮报的 2.4% 是**分子按实例、分母按文件**——同一任务出现在多个批次，两个分母差 2.7 倍。四类结果全记（含"执行了但正确地什么也没做"，以及"拒绝执行"记 UNKNOWN 而不记为无变化）。
- **账本能说出"哪次任务"**：目标第五步要求记录"哪次任务检索了它、改变了什么行动、结果怎样"，而账本每条 run_id 都是同一个演示标签——**"哪次任务"的答案是标签不是任务**。原因是复用审计把结果写进报告文件、别处一字没有，**一份省略了使用过程的使用记录，会让"有复用证据"和"从没试过"长得一样**。现在每个任务实例各写 RETRIEVED / APPLIED / OUTCOME 三行：**7 个真实任务 ID，0 → 7**。
- **"过时"是双向的，而只有一边安全**：记录**窄于**测量只是少一次复用；记录**宽于**测量会把没人测过的任务族当成适用场景，而检索照着这个声称行动——**过量声明就变成一次没有证据的应用**。首版只算"少声明"那一半，于是过量声明**通过了复核**；现在两个方向都判、都能被修订收窄，且 `apply()` 真的执行修订而不只是报告。
- **"修订"不再是空头承诺**：版本管理文档里写着 RETIRE / REVISE / KEEP 三个转换，实际只有两个。第三个覆盖的正是**真实会发生**的情形——条目没害处，但**记录比后来的测量窄**（测量是激活时的快照）。修订**只改测量范围**，教训正文一字不动（否则那是套着版本号的第二次未审核启用），旧版本保留、链仍校验、且**会收敛**。
- **规划器有了第一个可离线测量的效果**：规划器自己的 SYSTEM PROMPT 写着"若指令固定了顺序就照做"，而校验函数**只查名字认不认识**——这句话从未被验证。归档里唯一那次顺序倒置是**跑完整轮之后**才发现的。现在计划侧直接拒绝倒置的计划：16 份合规计划 **0 误拒**，那次跨任务重排被抓到；指令没规定顺序时**完全不动**。
- **量到了就必须送得到**：复用审计测出这条经验在 **T12（3 个）与 T03（1 个）**实例上有效，而检索门按 `task_family` **精确匹配**，4 次胜利**一次也送不出去**。同一条链底下还有第二个缺陷：`task_family` 是**硬编码默认值**，于是从 **T05** 批次学到的 harness 教训声明自己是 **T13** 教训——检索照着这个标签行动，条目**被发给错的族、同时对对的族不可见**。现改为**由证据推导**（批次名或运行 template_id，推不出即拒绝生成），并记录 `measured_families`；检索发给已量到的 T13/T12/T03，仍扣留未量过的 T14，在 T12+T03 的 **18 个**低于契约计划上修好 **18/18**。
- **复用是在没建过它的任务上测的**：编译后的技能资产跑遍整个归档，从 **T13** 的失败上学到的经验也修好了 **T12（3 个实例）与 T03（1 个）**，共 **7 个不同实例、跨 3 个任务族**，**弄坏 0 个、未触碰任何本来合格的计划**。报告自己声明这是**跨任务族复用**而非跨 split 迁移。
- **仍未做**：跨 split 迁移——目前没有一条"开发集学、held-out 测"的经验。
- 因此本计划书**不主张**"经验复用带来任务成功率提升"，只主张**通道已接通且每一步可被第三方复算**。
